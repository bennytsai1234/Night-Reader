### 背景工作的生命週期

ADR 0058 的四件背景工作與 ADR 0070 放到背景的搜尋，加上頁面那層。

**改前**（2026-11-19，`beta` `a68a1cc9`）：

| 位置 | 旗標 |
|---|---|
| AI 找書 `lib/core/ai_find/ai_find_session.dart` | `_started`、`_stopped`、`_pausing`、`_paused`、`_disposed` |
| 單一書源 AI 修復 `lib/core/ai_repair/ai_repair_session.dart` | `_running`、`_stopped`、`_paused`、`_disposed`、`_committing` |
| 修復異常書源 `lib/core/ai_repair/source_repair_batch.dart` | `_running`、`_stopped`、`_paused`、`_disposed`、`_editing` |
| 頁面那層 `lib/features/source_manager/ai_repair/repair_runs.dart` | `_started`、`_finished`、`_seen`、`_paused`、`_resuming`、`_ending` |

「正在暫停」有四種寫法：AI 找書是 `_pausing && !_paused`，兩種修復是 `_paused && _running`，校驗是 `_pausing && !_ending`，搜尋是 `_Settling.pausing`；通知與頁面上的「正在暫停…」「正在結束…」各自照自己的旗標拼出來。

**階段表**（讀者看到的，照 ADR 0058、0070 與 `docs/design/components.md`「狀態用詞」、`screens.md` 各頁定；五件共用）：

| 階段 | 讀者看到什麼 | 可以走到 | 現在一樣嗎 |
|---|---|---|---|
| 未開始 | 頁面剛推入，推入動畫還沒播完；沒有通知 | 做著 | 一樣 |
| 做著 | 通知：標題、做到哪、「暫停」「結束」；頁面：「暫停｜結束」（校驗在書源管理的狀態列，搜尋在進度那一列） | 正在暫停、正在結束、做完 | 一樣 |
| 正在暫停 | 通知內文「正在暫停…」、按鈕拿掉；頁面「正在暫停…」灰掉，「結束」還能按 | 已暫停、正在結束（結束蓋過暫停）、做完（停不下來的那一步做完就是做完，例如正在存修好的書源） | 不一樣：修書源在這時按結束，紀錄與停在半途的 AI 修復不對（下面兩件 bug） |
| 正在結束 | 通知內文「正在結束…」、按鈕拿掉；頁面「正在結束…」灰掉 | 做完 | 一樣 |
| 已暫停 | 通知收掉、位置空出來；頁面「已暫停」與「繼續｜結束」，別件在跑時「繼續」灰掉；被系統收掉、從最近使用滑掉，下次開 App 也是這裡 | 讀回中、正在結束、做完（修書源與校驗開始新的一件時） | 一樣 |
| 讀回中 | 頁面照舊是已暫停，「繼續」灰掉 | 做著、已暫停（接不下去，例如書源不在了）、正在結束 | 一樣 |
| 做完 | 通知收掉；頁面是結果與「完成」 | 看過結果、頁面都關了才放掉（入口改成開新的一件） | 一樣 |

剪貼簿的 AI 修復另有「等貼回」：不是背景工作、沒有通知，只在修復頁上。

**暫停的回饋要不要一致**：一致，五件都照上表。ADR 0058 定的通知（按了內文變「正在暫停…」「正在結束…」、按鈕拿掉）與 `components.md`「狀態用詞」（按了還沒停好時寫「正在暫停…」「正在結束…」，不能再按、灰掉）本來就是五件共用的規則；讀程式與偵測測試確認五件的頁面與通知已經照做，「只有 AI 找書有正在暫停」是內部旗標的差別，讀者看不到。正在暫停時還能按結束、結束蓋過暫停，照放到背景的搜尋已有的規則，五件一起。

**誰記哪個階段**：工作本身（找書、單一修復、整批、校驗、搜尋）記它自己做著、正在暫停、正在結束、已暫停、做完，因為停不停得下來只有它知道（存修好的書源時停不下來）；頁面那層只記工作不知道的：未開始、讀回中、暫停中按了結束、和工作回來之後是已暫停還是做完。頁面與通知讀頁面那層算出的一個階段，不各自拼旗標。

**不收進階段的**（會和階段同時成立）：

- `_disposed`、`_isDisposed`：物件放掉了，任何階段都可能。
- `_committing`：正在存修好的書源，和做著、正在暫停、正在結束同時成立；是「這一段停不下來」的名字，不是階段。
- `_editing`：做完之後在結果頁刪書源中，只在做完時成立。
- `_seen`、開著的頁數：有沒有人看過結果，和做完同時成立。
- 放到背景的搜尋的 `_abandoned`、`_headerWritten` 與 `search_run.dart` 的旗標：屬於搜尋那個候選，這次不動。

**歷史上因此出錯的**：

- #398：按了停止到結果寫完之間重讀清單，剛做完的校驗結果被當成過期丟掉；原因是看「正在校驗」（`_isChecking`），該看「這一輪還沒做完」（`_runInProgress`）。
- #390 審查：繼續讀回期間按結束，晚到的新工作照樣換上去。
- #390 審查：開 App 讀回時只在等待前檢查，等待後沒再檢查。
- #390 審查：暫停中的修復頁，別件做完「繼續」還是灰的。
- #353：頁面返回時直接釋放還在跑的工作，改成先停止、等結束再關。

查過不算：#358 停止閃退是結束 isolate 的方式（`Isolate.immediate`），和旗標無關。

**重構時查到並修掉的**：

- 單一書源 AI 修復正在存修好的書源時先按暫停再按結束：紀錄先寫「已結束，書源沒有改」、再寫「修好了」。原因是結束看 `_paused` 走「已經暫停好」的捷徑，沒看 `_running`。
- 修復異常書源暫停後（或正在暫停時）按結束：整批收尾了，停在半途的那件 AI 修復仍是「已暫停」，點進去「結束」還能按；正在暫停時整批還在跑就先標成做完。原因同上，捷徑也沒有結束那幾件修復。
- 放到背景的搜尋按了暫停、還在等結果檔寫完時按結束：照開始等之前的判斷停成已暫停，沒寫上結束的那一行，之後還能繼續。原因是等寫檔前就決定了要暫停，等完沒再看一次。
- 校驗正在暫停時，書源管理的狀態列落回上次的摘要、「結束」灰掉，直到暫停好。原因是狀態列只看校驗服務「校驗中」，校驗服務在按暫停那一刻就不算校驗中了，這次校驗卻還沒停好。
- 校驗流程本身出錯（讀書源出錯、記錄這個錯時又讀不到）後，校驗服務一直停在「校驗中」，之後的校驗與登入後的自動校驗都直接回傳舊摘要。原因是例外跳過了收尾。

換結構時自己弄出、合併前修掉的（Codex 審查找到）：按了結束、工作本身做完、頁面那層還在刪存檔時，通知換回「暫停」「結束」；校驗流程出錯時，按了停止的那種也會卡在「停下中」（改前按了停止反而能開始下一輪）。

**改後**：

| 位置 | 改後 |
|---|---|
| 共用 `lib/core/background_work/work_phase.dart` | `WorkPhase`：還沒開始、做著、正在暫停、正在結束、已暫停、讀回中、等貼回、做完 |
| AI 找書、單一書源 AI 修復、修復異常書源 | 各一個 `WorkPhase`，只用到自己有的幾個；做著的那一步看「正在暫停或結束」收手；一段跑完照結果與按了什麼定下一個 |
| 頁面那層 | `_RunStage`：未開始、工作在跑、已暫停、讀回中、暫停中按了結束、做完；`run()` 直接回傳暫停好了還是做完；對外的 `phase` 在工作跑的時候照工作本身；通知的「正在暫停…」「正在結束…」在這裡統一換 |
| 放到背景的搜尋 | `_Settling` 換成 `WorkPhase`（做著、正在暫停、正在結束） |
| 從書源管理按的校驗 | `WorkPhase`：做著、正在暫停、正在結束，跑完記成已暫停或做完 |
| 校驗服務 | `_CheckPhase`：閒著、校驗中、停下中；開始新的一輪要閒著 |

頁面的按鈕列、狀態列與通知只讀階段。工作本身已經停好、頁面那層還在收尾時，頁面讀到它要去的那一頭（正在暫停或正在結束），通知不再更新、等收掉。讀者看得到的差別，都是照階段表把五件拉齊：

- AI 找書正在暫停時按結束：原本「暫停」那列還寫「正在暫停…」、下面又寫「正在結束…」，現在照其他四件，「暫停」灰掉、「結束」寫「正在結束…」。
- 已暫停的搜尋按結束、還在寫結束的那一行時：進度那一列原本仍寫「已暫停」，現在寫「正在結束…」。
- 上面三件修掉的 bug。

改測試的兩處（讀者看不到的舊意思）：沒開始就結束的一批，通知原本寫「正在結束…」；做完的一批原本仍算「按了結束」。現在「正在結束」只在還沒停好時成立。

### 有聲書播放器

ADR 0055 的播放器（`lib/features/audiobook/audiobook_player.dart`），讀它的是播放器頁、收聽圓鈕與系統播放資訊。

**改前**（2026-11-20，`beta` `660b61a1`）：

| 旗標 | 意思 | 誰設 |
|---|---|---|
| `_playing` | 引擎回報在播 | 引擎的 `playingStream`；換集失敗、播放出錯、停止時直接設 false |
| `_loading` | 開書或換集中 | 開書、換集開始時 true，載完或失敗時 false |
| `_buffering` | 引擎在等資料 | 引擎的 `bufferingStream`；停止時 false |
| `_ended` | 最後一集播完 | 播完沒有下一集時 true，開書、換集時 false |
| `_error` | 最後一次失敗的原因 | 開書失敗、換集失敗、播放途中出錯 |
| `_wantPlay` | 使用者要不要出聲 | 播放、換集 true；暫停、失敗、停止 false |
| `_generation` | 哪一次載入還有效 | 開書、換集、停止、放掉時加一 |

階段散在組合裡：「打不開」是 `_chapters.isEmpty && _error != null`（播放器頁與 `open()` 各寫一次），「這一集播不出來」是有目錄又有 `_error`，「真的在出聲」是 `_playing && !_buffering && !_loading`，「回到前景可以接另一台的進度」是 `!_playing && !_loading && _chapters.isNotEmpty`。播放鍵、系統的播放鍵與收聽圓鈕都走 `toggle()`，它只看 `_playing`；載入中 `_playing` 是 false，按下去照「暫停中按播放」讓引擎播，播的是還沒換掉的上一集。

**歷史上因此出錯的**：

- #327 審查：載入中按暫停，載入完仍自己開始播（只有 `_loading`，沒記使用者要不要出聲，加了 `_wantPlay`）。
- #327 審查：收聽計時與定時在緩衝時照算（定時只看 `_playing`，沒看 `_buffering`）。
- #327 審查：換到抓不到的一集時畫面停在新集、耳朵還聽著舊集（換集失敗只設 `_error`，引擎照播）。
- #327：上次連目錄都沒開成，再開同一本不會重開（「打不開」沒有自己的狀態，加了 `_chapters.isEmpty && _error != null`）。
- #436：開書還在讀目錄、或目錄沒讀成時，「上一集」讀空清單丟錯、播放鈕畫成錯誤方塊；列表循環時「下一集」照樣亮著、按了卡在載入中；按播放、回到前景接進度也丟錯（「開書中」「打不開」只用空目錄表示，集數卻已經是上次那集）。審查另外留下沒修的一件：載入中按播放，引擎先接著播上一本停下的那一集。

查過不算：#345 把「記下書源」移到抓目錄之前（失敗畫面才給得出登入），是順序，和旗標無關；#327 的「從目錄點正在播的那集沒從頭播」是集數比較。

**階段表**（照 ADR 0055 與 `docs/design/audiobook.md` 定）。按鍵怎麼走：播放器底部膠囊的播放鍵與收聽圓鈕走 `toggle()`（播著就暫停，其他就播放）；系統的播放鍵照交出去的狀態叫播放或暫停；系統的拖動、倒退、快轉和進度條一樣走拖動。「現在一樣嗎」比的是換結構前的程式：

| 階段 | 播放器頁 | 收聽圓鈕 | 系統播放資訊 | 可以走到 | 現在一樣嗎 |
|---|---|---|---|---|---|
| 沒有書 | 還沒開這本：清單是骨架 | 收起 | 收掉 | 開書中 | 一樣 |
| 開書中（讀書源、目錄與上次聽到哪） | 清單是骨架，播放鍵轉圈 | 播放圖示 | 不動（上一本停止時已收掉） | 載入這一集、打不開、沒有書、開書中（開別本） | 不一樣：按播放鍵時，播過別本的引擎會先出聲（播的是停掉的上一本） |
| 打不開 | 清單的位置是「有聲書打不開」、原因與「重試」（要登入或驗證時是「登入」「前往驗證」） | 播放圖示 | 不動 | 開書中（重試、按播放、再開同一本）、沒有書 | 不一樣：按播放鍵、點圓鈕沒反應 |
| 載入這一集（找下載好的檔、抓網址、開音訊） | 清單，播放鍵轉圈 | 播放圖示 | 抓網址時停在上一集、暫停；開音訊時引擎回報等資料或總長，換成這一集、等資料（第一次開書時還沒有） | 播著或暫停（載好，照使用者最後要不要出聲）、這一集播不出來、載入這一集（換別集）、沒有書 | 不一樣：按播放鍵時引擎接著播還沒換掉的上一集；拖動拖的是上一集、位置記到這一集；上一集晚到的錯讓這一集播不出來 |
| 播著 | 暫停圖示；緩衝時轉圈 | 暫停圖示 | 播放中；緩衝時寫等資料 | 暫停、載入這一集（換集、播完接下一集）、播完、這一集播不出來、沒有書 | 不一樣：單集循環（與隨機只剩這一集）播完重播前，存進度的那一下按暫停、換集或停止，舊的這一集照樣出聲 |
| 暫停 | 播放圖示；緩衝時轉圈 | 播放圖示 | 暫停，停在哪 | 播著、載入這一集（換集、回到前景接另一台的進度）、這一集播不出來、沒有書 | 不一樣：回到前景接進度的途中按了播放，接進度蓋掉這次播放、停著不播 |
| 這一集播不出來 | 清單照舊，跳一則提示寫原因（要登入或驗證時旁邊給那一顆），播放圖示 | 播放圖示 | 暫停 | 載入這一集（按播放重載、換集、回到前景接進度）、沒有書 | 一樣 |
| 播完（最後一集播完，播完停） | 播放圖示，進度在結尾 | 播放圖示 | 暫停 | 暫停（拖動）、載入這一集（按播放從這一集開頭、換集、回到前景接進度）、沒有書 | 不一樣：拖進度條之後按播放，還是從開頭播 |

改後「不一樣」的那幾格照這樣做：開書中與載入這一集按播放只記下要出聲，載好照最後的意思播不播；這兩個階段拖動不做事、引擎送來的錯不算這一集的；打不開時按播放就是重試；叫引擎出聲的地方都先看使用者還要不要出聲、還是不是這一集；回到前景接進度時抓的途中按過什麼就不跳；播完後一拖就回到暫停、停在拖到的地方。

**刻意維持現狀的畫面**：載入中播放鍵轉圈、圓鈕與系統播放資訊是播放圖示，所以載入中沒有地方按暫停（只有別的播放接手時會暫停）。要改成載入中照「要不要出聲」畫暫停圖示、按了就不播，得看圖選，這次不動。

另一處：開書中、載入這一集時拖動不做事之後，播放器的進度條與倒退、快轉 10 秒照 ADR 0059 該灰掉，現在仍亮著、按了沒反應。灰掉要看圖選，這次不動。

**不收進階段的**（會和階段同時成立）：

- 緩衝（`_buffering`）：引擎回報在等資料，播著與暫停時都可能（暫停中拖動也會等資料）；播放鍵轉圈、系統播放資訊寫等資料、收聽時間與定時不算。
- 使用者要不要出聲（`_wantPlay`）：每次載入開始時定下（換集、重播是要，接另一台的進度是不要，開書、播完接下一集照當時的意思），載入途中按的播放或暫停蓋過它，載好只看它；暫停時在接手系統播放的那一下也看它。別的播放接手、定時到了都只改它。
- 哪一次載入還有效（`_generation`）：每次開書、換集、停止加一，每個等待之後拿它比，比不上就是被後來的動作取代了；階段相同時也要分得出是哪一次（例如兩次換集都在載入這一集）。
- 使用者按過幾次（`_commands`）：開書、播放、暫停、拖動、換集、停止各加一（含系統的按鍵與定時到了）。回到前景接另一台的進度要知道抓的途中有沒有按過什麼；按了播放還在等系統接手時，階段、集數與位置都還沒變，看不出來。

**重構時查到並修掉的**（表上寫「不一樣」的格子與 Codex 審查找到的，各一個提交，先寫會失敗的測試）：

- 載入中（開書中、載入這一集）按播放鍵、收聽圓鈕或系統的播放鍵，引擎先接著播還沒換掉的上一集（或停掉的上一本）。原因是 `play()` 只分「失敗或播完」與「其他」，載入中落進「暫停中按播放」。
- 單集循環（與隨機只剩這一集）播完重播前，存進度的那一下按暫停（含定時到了、別的播放接手）、換集或停止，舊的這一集照樣出聲。原因是重播直接叫引擎播，沒經過看「還要不要出聲」的那道關。
- 最後一集播完後拖進度條再按播放，還是從開頭播；引擎還沒拖好就按播放也是。原因是 `_ended` 只在開書、換集時清掉，拖動不會。
- 整本打不開時按播放鍵、點收聽圓鈕沒反應。原因是第一次開書就失敗時沒有引擎、直接返回；播過別本時重載這一集又因為沒有目錄不做事。
- 回到前景接另一台的進度時，抓的途中按了播放（重載播不出來的那一集，或還在等系統接手），抓回來照樣跳過去、蓋掉這次播放、停著不播，還記成同步過。原因是抓回來後只用 `_playing`、集數與位置猜有沒有按過，這兩種情況三樣都還沒變。
- 載入途中按的播放或暫停被蓋掉：接另一台的進度時按播放，載好仍停著；開書中或按了暫停之後才報播完，開書與接下一集又把「要出聲」設回去。原因是載好播不播看「這次是不是自動播」和 `_wantPlay` 兩件同時成立。
- 換集途中（存進度、等上一集停聲）停止或開了別本，舊的換集回來讀清空的目錄丟錯，或拿新書的目錄換到同一個集數。原因是換集等完才記下「這一次」。
- 換集抓網址時拖動（含系統的），拖的是引擎裡的上一集，拖到的位置被記成新的一集聽到哪。原因是拖動只看有沒有書與引擎。
- 換集抓網址時引擎送來上一集的錯，被算成新的一集播不出來。原因是引擎的錯不分是哪一集的，任何階段都採用。

換結構前補的偵測測試有一項寫下的是最後一件的舊行為（留著原因、不播），判斷舊的是錯的，改了測試。

抓書源的結果什麼時候換：進頁或重新載入、閱讀器換了源、這頁換源、檢查更新成功時清掉；書籍資訊抓失敗時記成「沒更新到」（已經有目錄的問題時不蓋），抓到時收掉；目錄抓失敗時記成「沒抓到」或「擋在登入牆後」。目錄後來有了不用另外清，顯示時就不寫。重讀書源不動它。預下載、檢查更新因為書源不能讀被擋時，理由只看書源本身。

讀者看得到的差別是上面的 bug；另外換源換到的書源本身不能讀時那一列改寫它的健康說明（原本不寫），只在換源清單列出之後書源才變成不能讀時碰得到。偵測測試沒有改到期待值，只把讀「檢查更新中」「更新書架中」的兩處換成 `isRunning(...)`。

換結構時自己弄出、合併前修掉的（Codex 審查找到）：重讀書源改成保留抓書源的結果之後，書源拿掉登入或被刪掉，那一列還掛「登入」；書源停用後預下載、檢查更新的被擋理由寫成舊的目錄提示；重抓回零章時當成抓到、那一列收掉。同一次審查找到改前就有的兩件（上面清單最後兩件），一起修了。

查過、沒修的：檢查更新途中書被移出書架或換了源，更新服務略過寫回、回報成功，詳情照成功收掉「書籍資訊更新失敗」；要更新服務另外回報「略過」才分得出來，碰到的時機很窄，留著。

### 同步

`lib/core/sync/sync_service.dart` 決定什麼時候跑哪一種同步（ADR 0039、0046）：日常只同步閱讀進度，「立即全面同步」與剛選好同步空間時同步全部種類；同一時間只跑一段，途中又有人要就排著，跑完再補；全面同步可以取消，在兩種資料之間停。

**改前**（2026-11-20，`beta` `660b61a1`）：

| 旗標 | 意思 | 什麼時候成立 |
|---|---|---|
| `_running`（`Future?`） | 有一段同步在跑（含途中補跑的輪次） | 從要求到最後一輪做完；`_finishRun` 掛在 `whenComplete` 上放下 |
| `_again` | 跑的途中又有人要同步 | 只在跑的時候設；每輪開始清掉 |
| `_fullPending` | 有人要全面同步、那一輪還沒開始 | 跑的時候和 `_again` 一起設；閒著時要求的，第一輪開始前就取走 |
| `_cancelled` | 使用者取消了這一輪全面同步 | 按了取消到下一輪開始；進度輪裡按也會設，只是沒作用 |
| `_progressFirst` | 有人要閱讀進度插隊先送 | 離開閱讀器、有聲書存進度時設；做進度那一種時清掉 |
| `_authorizingGoogleDrive` | Google 登入畫面開著 | 選 Google 雲端硬碟的那段；這段期間回到前景、退到背景都不同步 |

「這一輪是全面同步」只活在 `_runUntilSettled` 的區域變數，「排著的是全面同步還是進度」要看 `_again` 與 `_fullPending` 兩個一起；取消把 `_fullPending` 清掉、`_again` 留著，排著的全面同步就變成一輪進度同步。進度框按下取消後的「正在停下…」與收掉後那行提示，是進度框自己記的「按過取消」加上整段跑完後的 `status.error` 拼出來的，不是服務告訴它的。

**歷史上因此出錯的**（`git log -G'bool _旗標名'` 找到的都是加旗標的那個功能或修正：#194 `_again`、#232 `_authorizingGoogleDrive`、#235 `_progressFirst`、#257 `_fullPending` 與 `_cancelled`；之後動到這幾個旗標的提交只有 #199、#208 改收尾，打開 diff 都不是修旗標組合）：

- #257 審查：「同步結束」的通知裡又要求全面同步，拿到的是剛結束那一段的 future，要求的全面同步沒跑。原因是狀態已經寫成結束、`_running` 還沒放下；改成先放下再通知。

查過不算：#232 審查的「補跑的輪次之間 `running` 不閃成 false」是補測試，當時的程式沒錯。

**階段表**（讀者看到的，照 ADR 0046 與 `docs/design/screens.md`「備份與同步」定）：

| 階段 | 讀者看到什麼 | 可以走到 | 現在一樣嗎 |
|---|---|---|---|
| 閒著 | 「立即全面同步」的副標是上次全面同步的時間或失敗原因；沒有進度框 | 同步進度、全面同步 | 一樣 |
| 同步進度 | 副標「同步中（1/1）：閱讀進度」；開 App、回到前景時開書等它做完進度那一步 | 閒著；排著的是進度或全面時，直接進那一輪 | 一樣 |
| 全面同步 | 進度框「全面同步中」、進度條與正在同步哪一種、「取消」；副標同上 | 停下中、閒著；排著的是進度或全面時，直接進那一輪 | 一樣 |
| 停下中 | 進度框「正在停下…」灰掉；手上這一種做完就停，寫完的留著 | 閒著；排著的是進度（取消降成的）或取消之後才要求的全面時，直接進那一輪 | 不一樣：最後一種做著時按取消，其實全部做完、上次全面同步的時間也更新了，提示卻寫「已停下」 |

輪與輪之間直接換，中間不經過閒著、也不通知閒著。`status.phase` 在下一輪拿到同步空間、真的開始前，還是上一輪的階段。

**排著的下一輪**（跑的途中又有人要，和上面的階段同時成立，另記）：沒有、同步進度、全面同步。同時要過進度與全面同步時排全面同步，它含進度。取消把排著的全面同步降成同步進度：排的時候可能也有人要過進度（退到背景、有聲書存好進度），分不出來就照要過算，不漏送。

| 排著 | 讀者看到什麼 | 現在一樣嗎 |
|---|---|---|
| 全面同步排在日常同步後面 | 進度框已經開著，寫「全面同步中」與日常那一輪的進度；按取消就不跑 | 不一樣：取消後要等日常那一輪、再加一輪補跑的進度同步做完，進度框才收 |
| 同步進度排在全面同步後面 | 進度框照全面那一輪走 | 不一樣：全面那一輪做完，還要等補跑的進度輪做完才收；ADR 0046 只要求至少等到全面那一輪 |

**進度框收掉後那一行**照這次要求的那一輪全面同步怎麼結束：做完是「全面同步完成」，取消停下是「已停下，同步好的資料留著」，失敗是「全面同步失敗：原因」。現在不一樣：那一行是進度框自己記的「按過取消」加上整段跑完後的 `status.error` 拼的，所以除了上面「停下中」那件，還有三種會寫錯：

- 全面那一輪有一份檔被拒絕，補跑的進度輪成功、把錯清掉，寫成「全面同步完成」。
- 全面那一輪成功，補跑的進度輪失敗，寫成「全面同步失敗」。
- 之前日常同步留下的錯還在，這次全面同步取消了（取消不清錯），寫成「全面同步失敗：舊原因」。

**不收進階段的**（會和階段同時成立）：

- `_progressFirst`：閱讀進度插隊，在全面同步或停下中的任何一種做完後都可能成立。收進跑著的那一段同步裡，整段做完就跟著放掉，閒著時不會留著。
- `_authorizingGoogleDrive`：Google 登入畫面開著，和有沒有在同步無關（登入時日常同步可能正在跑）。選同步空間那頁在登入中把按鈕停用，不會疊兩次。
- `_progressPending`：開書在等進度那一步，跟著開 App 與回到前景，和哪一輪無關。
- 「有一段在跑」和「讀者看到同步中」不是同一件事：沒設同步空間時一段同步照樣跑完（什麼都不做），副標不寫同步中。

**重構時查到並修掉的**：

- 進度框要等整段同步做完才收：全面同步途中退到背景、有聲書存好進度排了一輪進度同步，全面那一輪做完還要等它；全面同步排在日常同步後面時按取消，也要等日常那一輪再加一輪補跑。原因是 `syncAll()` 傳回的是整段的 `_running`，不是自己那一輪。
- 回到 App 時開書可能等到前一輪的進度（Codex 審查找到，改前就有）：退到背景或開 App 的那一輪還在讀雲端時回到 App，前一輪做完進度就放掉回來時的等待，開書照回來之前的雲端開、晚到的進度也不接；「同步結束」的通知裡回到 App 的，收尾接著把新的等待放掉。原因是開書的等待是一個共用的值，任何一個進度步驟或收尾都放它，沒記是哪一次要求的。
- 全面同步做到 AI 找書（ADR 0060）那一種時，進度寫「資料」：種類名稱的對照漏了它（Codex 審查找到，改前就有）。
- 進度框收掉後那一行是進度框自己拼的（「按過取消」加整段跑完後的 `status.error`），四種寫錯：
  - 最後一種做著時按取消：其實全部做完、上次全面同步的時間也更新了，卻寫「已停下」。
  - 全面那一輪有一份檔被拒絕、補跑的進度輪成功把錯清掉：寫成「全面同步完成」。
  - 全面那一輪成功、補跑的進度輪失敗：寫成「全面同步失敗」。
  - 之前日常同步留下的錯還在、這次取消了：寫成「全面同步失敗：舊原因」。

**改後**：

| 位置 | 改後 |
|---|---|
| `lib/core/sync/sync_service.dart` | `SyncPhase`：閒著、同步進度、全面同步、停下中。`_SyncRun`（null 就是閒著）記這一輪的階段、排著的下一輪（沒有、進度、全面）、進度插隊，與等這一輪和排著那一輪全面同步結果的人 |
| `SyncStatus` | `running` 換成 `phase`，`running` 由它算出；只在有同步空間、這一輪真的開始時寫成同步中 |
| 開書等待（`progressReady`） | 進度那一步開始時記下當時在等的那一個，做完只放它；回到前景換新的等待，舊的跟著新的放；整段收尾先取下這一段的等待再通知 |
| `syncAll()` | 傳回要的那一輪全面同步的 `FullSyncResult`（做完、停下、失敗與原因）；排著時取消就馬上傳回停下 |
| 進度框 `lib/features/settings/full_sync_dialog.dart` | 「正在停下…」讀 `phase`，收掉後那一行讀結果，不再自己記取消 |

最後一次看排隊和放下 `_SyncRun` 在同一段同步程式裡（改前放下掛在 `whenComplete` 上），先閒著再通知照舊，#257 那件寫不出來。讀者看得到的差別只有上面修掉的幾件：進度框在全面那一輪做完（或排著時取消）就收，收掉後那一行照那一輪的結果寫。

換結構時自己弄出、合併前修掉的（Codex 審查找到）：取消先發布「停下中」才把排著的全面同步降級，聽到通知才要求的全面同步會被同一次取消吃掉。總耗時的日誌原本在最後一次看排隊和放下之間，一起移到放下之後（日誌委派只有書源 isolate 會設，同步服務碰不到）。

查過不修：兩個全面同步進度框疊在一起時，先做完的那個 `pop` 會關掉上面那個。進度框有遮罩、按返回關不掉，正式的三個入口（立即全面同步、選好 Google 雲端硬碟、存好 WebDAV）疊不出兩個框，改前也是同樣的 `pop`。

改測試的兩處：排著時取消的偵測測試，進度框原本等日常那一輪做完才收，現在馬上收；插隊送進度的測試，A 的全面同步做完時補跑的那一輪還在跑，B 要等它做完才開始。
