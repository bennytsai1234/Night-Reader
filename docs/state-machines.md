ADR 0058 的四件背景工作與 ADR 0070 放到背景的搜尋，加上頁面那層。

| 單一書源 AI 修復 `lib/core/ai_repair/ai_repair_session.dart` | `_running`、`_stopped`、`_paused`、`_disposed`、`_committing` |

「正在暫停」有四種寫法：AI 找書是 `_pausing && !_paused`，兩種修復是 `_paused && _running`，校驗是 `_pausing && !_ending`，搜尋是 `_Settling.pausing`；通知與頁面上的「正在暫停…」「正在結束…」各自照自己的旗標拼出來。

**階段表**（讀者看到的，照 ADR 0058、0070 與 `docs/design/components.md`「狀態用詞」、`screens.md` 各頁定；五件共用）：

| 階段 | 讀者看到什麼 | 可以走到 | 現在一樣嗎 |
|---|---|---|---|
| 未開始 | 頁面剛推入，推入動畫還沒播完；沒有通知 | 做著 | 一樣 |
| 做著 | 通知：標題、做到哪、「暫停」「結束」；頁面：「暫停｜結束」（校驗在書源管理的狀態列，搜尋在進度那一列） | 正在暫停、正在結束、做完 | 一樣 |
| 正在暫停 | 通知內文「正在暫停…」、按鈕拿掉；頁面「正在暫停…」灰掉，「結束」還能按 | 已暫停、正在結束（結束蓋過暫停）、做完（停不下來的那一步做完就是做完，例如正在存修好的書源） | 不一樣：修書源在這時按結束，紀錄與停在半途的 AI 修復不對（下面兩件 bug） |
| 正在結束 | 通知內文「正在結束…」、按鈕拿掉；頁面「正在結束…」灰掉 | 做完 | 一樣 |
| 已暫停 | 通知收掉、位置空出來；頁面「已暫停」與「繼續｜結束」，別件在跑時「繼續」灰掉；被系統收掉、從最近使用滑掉，下次開 App 也是這裡 | 讀回中、正在結束、做完（修書源與校驗開始新的一件時） | 一樣 |
| 讀回中 | 頁面照舊是已暫停，「繼續」灰掉 | 做著、已暫停（接不下去，例如書源不在了）、正在結束 | 一樣 |
| 做完 | 通知收掉；頁面是結果與「完成」 | 看過結果、頁面都關了才放掉（入口改成開新的一件） | 一樣 |

剪貼簿的 AI 修復另有「等貼回」：不是背景工作、沒有通知，只在修復頁上。

**暫停的回饋要不要一致**：一致，五件都照上表。ADR 0058 定的通知（按了內文變「正在暫停…」「正在結束…」、按鈕拿掉）與 `components.md`「狀態用詞」（按了還沒停好時寫「正在暫停…」「正在結束…」，不能再按、灰掉）本來就是五件共用的規則；讀程式與偵測測試確認五件的頁面與通知已經照做，「只有 AI 找書有正在暫停」是內部旗標的差別，讀者看不到。正在暫停時還能按結束、結束蓋過暫停，照放到背景的搜尋已有的規則，五件一起。

**誰記哪個階段**：工作本身（找書、單一修復、整批、校驗、搜尋）記它自己做著、正在暫停、正在結束、已暫停、做完，因為停不停得下來只有它知道（存修好的書源時停不下來）；頁面那層只記工作不知道的：未開始、讀回中、暫停中按了結束、和工作回來之後是已暫停還是做完。頁面與通知讀頁面那層算出的一個階段，不各自拼旗標。

**不收進階段的**（會和階段同時成立）：

- `_disposed`、`_isDisposed`：物件放掉了，任何階段都可能。
- `_committing`：正在存修好的書源，和做著、正在暫停、正在結束同時成立；是「這一段停不下來」的名字，不是階段。
- `_editing`：做完之後在結果頁刪書源中，只在做完時成立。
- `_seen`、開著的頁數：有沒有人看過結果，和做完同時成立。
- 放到背景的搜尋的 `_abandoned`、`_headerWritten` 與 `search_run.dart` 的旗標：屬於搜尋那個候選，這次不動。

**歷史上因此出錯的**：

- #398：按了停止到結果寫完之間重讀清單，剛做完的校驗結果被當成過期丟掉；原因是看「正在校驗」（`_isChecking`），該看「這一輪還沒做完」（`_runInProgress`）。
- #390 審查：繼續讀回期間按結束，晚到的新工作照樣換上去。
- #390 審查：開 App 讀回時只在等待前檢查，等待後沒再檢查。
- #390 審查：暫停中的修復頁，別件做完「繼續」還是灰的。
- #353：頁面返回時直接釋放還在跑的工作，改成先停止、等結束再關。

查過不算：#358 停止閃退是結束 isolate 的方式（`Isolate.immediate`），和旗標無關。

**重構時查到並修掉的**：

- 單一書源 AI 修復正在存修好的書源時先按暫停再按結束：紀錄先寫「已結束，書源沒有改」、再寫「修好了」。原因是結束看 `_paused` 走「已經暫停好」的捷徑，沒看 `_running`。
- 修復異常書源暫停後（或正在暫停時）按結束：整批收尾了，停在半途的那件 AI 修復仍是「已暫停」，點進去「結束」還能按；正在暫停時整批還在跑就先標成做完。原因同上，捷徑也沒有結束那幾件修復。
- 放到背景的搜尋按了暫停、還在等結果檔寫完時按結束：照開始等之前的判斷停成已暫停，沒寫上結束的那一行，之後還能繼續。原因是等寫檔前就決定了要暫停，等完沒再看一次。
- 校驗正在暫停時，書源管理的狀態列落回上次的摘要、「結束」灰掉，直到暫停好。原因是狀態列只看校驗服務「校驗中」，校驗服務在按暫停那一刻就不算校驗中了，這次校驗卻還沒停好。
- 校驗流程本身出錯（讀書源出錯、記錄這個錯時又讀不到）後，校驗服務一直停在「校驗中」，之後的校驗與登入後的自動校驗都直接回傳舊摘要。原因是例外跳過了收尾。

換結構時自己弄出、合併前修掉的（Codex 審查找到）：按了結束、工作本身做完、頁面那層還在刪存檔時，通知換回「暫停」「結束」；校驗流程出錯時，按了停止的那種也會卡在「停下中」（改前按了停止反而能開始下一輪）。

**改後**：

| 位置 | 改後 |
|---|---|
| 共用 `lib/core/background_work/work_phase.dart` | `WorkPhase`：還沒開始、做著、正在暫停、正在結束、已暫停、讀回中、等貼回、做完 |
| AI 找書、單一書源 AI 修復、修復異常書源 | 各一個 `WorkPhase`，只用到自己有的幾個；做著的那一步看「正在暫停或結束」收手；一段跑完照結果與按了什麼定下一個 |
| 頁面那層 | `_RunStage`：未開始、工作在跑、已暫停、讀回中、暫停中按了結束、做完；`run()` 直接回傳暫停好了還是做完；對外的 `phase` 在工作跑的時候照工作本身；通知的「正在暫停…」「正在結束…」在這裡統一換 |
| 放到背景的搜尋 | `_Settling` 換成 `WorkPhase`（做著、正在暫停、正在結束） |
| 從書源管理按的校驗 | `WorkPhase`：做著、正在暫停、正在結束，跑完記成已暫停或做完 |
| 校驗服務 | `_CheckPhase`：閒著、校驗中、停下中；開始新的一輪要閒著 |

頁面的按鈕列、狀態列與通知只讀階段。工作本身已經停好、頁面那層還在收尾時，頁面讀到它要去的那一頭（正在暫停或正在結束），通知不再更新、等收掉。讀者看得到的差別，都是照階段表把五件拉齊：

- AI 找書正在暫停時按結束：原本「暫停」那列還寫「正在暫停…」、下面又寫「正在結束…」，現在照其他四件，「暫停」灰掉、「結束」寫「正在結束…」。
- 已暫停的搜尋按結束、還在寫結束的那一行時：進度那一列原本仍寫「已暫停」，現在寫「正在結束…」。
- 上面三件修掉的 bug。

改測試的兩處（讀者看不到的舊意思）：沒開始就結束的一批，通知原本寫「正在結束…」；做完的一批原本仍算「按了結束」。現在「正在結束」只在還沒停好時成立。

### 書源管理

書源管理頁的清單（`lib/features/source_manager/source_manager_provider.dart`）：誰正在讀、改書源，其他改書源的動作要不要等。

**改前**（2026-11-20，`beta` `660b61a1`）：

| 旗標 | 意思 | 誰設、誰收 |
|---|---|---|
| `_isLoading` | 清單在讀（一建立就是，等進場動畫播完才讀） | 讀清單（`loadSources` 預設會設）與匯入都設 |
| `_loadOwnsLoading` | `_isLoading` 是讀清單設的，不是匯入設的 | 最新一次讀清單收尾時，是自己設的才收 `_isLoading` |
| `_isBatchOperationInProgress` | 批次作業中（刪、移動、改分組、校驗、清標記） | 批次作業開頭設、結束收；裡面的重讀照樣再設 `_isLoading` |
| `_mergingDuplicates` | 讀清單時正在併重複書源（ADR 0062） | 讀清單裡設、併完收 |
| `_syncReloadPending` | 同步套用了別台的書源，重讀已經排著、等頁面露出來 | 收到同步通知時設、開始重讀前收 |

一起決定的四個問題，各自用不同的組合拼：

- 整份清單忙不忙（`isMutationBusy`，選單、多選工具列、分組管理灰掉）：`_isLoading` 或批次、校驗中、併重複書源、有一列在改。
- 這一列能不能按（`isSourceLocked`）：批次、校驗中、這一列在改；不看載入與併重複書源。
- 能不能開始改一列（`_beginSourceMutation`）：不在載入、不在批次、不在校驗；不看併重複書源。
- 能不能併重複書源：不在批次、不在校驗、沒在併、沒有一列在改；不看載入。

同時成立的有：批次作業裡的重讀（批次與載入都是真）、第一次讀清單時併重複書源（載入與併都是真）、匯入裡的重讀（`_isLoading` 是匯入的、重讀不收）。`_loadOwnsLoading` 就是為了分清楚最後一個。

**歷史上因此出錯的**：

- #33：切一個開關整個清單重建、所有開關變淡。清單用不用可拖曳的版面看 `isMutationBusy`，它把「有一列在改」也算進去；改成版面只看排序與篩選，單列修改只鎖那一列。
- #33：置頂、置底走單列修改，和別列的修改同時改寫全部書源的順序；改成批次作業獨占。
- #56：顯示載入中的讀取被背景的重讀（校驗做完）蓋過時，`_isLoading` 一直不收，清單永遠在載入。原本只有顯示載入中的那次讀取收得掉，被蓋過的又因為不是最新一次而不收；改成最新一次收尾就收，同時加 `_loadOwnsLoading`，免得收掉匯入設的。

查過不算：`_isLoading` 一建立就是真（#69）、`_syncReloadPending`（#235）、`_mergingDuplicates`（#380）都是新功能帶進來的，不是修旗標組合。

**階段表**（讀者看到的，照 ADR 0018、0024、0062 與 `docs/design/screens.md` 的書源管理；整份清單現在被誰占著）：

| 階段 | 讀者看到什麼 | 可以走到 | 現在一樣嗎 |
|---|---|---|---|
| 第一次讀 | 進場動畫播完才讀；骨架的列數與字照上次，搜尋框、多選工具列照上次有沒有書源留位置；選單灰掉 | 閒著（讀到清單，或讀不到時是錯誤頁與「重試」） | 一樣 |
| 閒著 | 都能按；切開關、刪一個書源時只鎖那一列，別列照樣能改 | 重讀、匯入、批次作業 | 一樣 |
| 重讀 | 改了書源之後、從編輯頁回來、按了「重試」時：清單留著（空的時候畫骨架，例如按了重試）；選單、多選工具列灰掉；列看起來能按，切開關不理 | 閒著 | 一樣（列看起來能按卻不理：維持，見下） |
| 匯入 | 寫進資料庫（含匯入自己併重複書源）：同重讀；頁面的匯入流程另有進度條、列灰掉 | 重讀（寫完；寫入出錯時較新的重讀還沒讀完）、閒著（寫入出錯） | 不一樣：不在閒著時按了匯入，提示「未匯入有效書源」，其實是書源管理正忙 |
| 批次作業 | 刪、移動、改分組、校驗、清標記：選單、工具列、每一列都灰掉，不能拖 | 閒著 | 一樣 |

**併重複書源**是有名字的動作，不是階段：它在讀清單裡做，會和第一次讀、重讀、閒著（背景重讀時）同時成立。併的時候：

| 誰 | 現在 | 照 ADR 0062 該怎樣 |
|---|---|---|
| 批次作業、匯入 | 不理 | 同現在 |
| 改一列（切開關、刪） | 照做：切了要留下的那個的開關，合併存回它時可能蓋掉；刪掉要留下的那個時，那組不併（合併在交易裡重查），或書剛搬過去它就被刪 | 不理，同重讀時 |
| 另一次讀清單 | 不併、直接讀：讀到併之前的清單，併完的那次又因為不是最新一次而丟掉結果，清單留著已經刪掉的重複書源；讀的途中合併跑完、讀到的是併之前的也一樣 | 等它併完再讀，讀完照常判斷要不要併 |
| 畫面 | 背景重讀時開始併不重畫，看起來是閒著 | 同現在 |

**誰收**：第一次讀與重讀由最新一次讀清單收尾時收；匯入與批次作業做完自己收，這時最新一次讀清單還沒讀完（背景重讀蓋過了自己的重讀）就換成重讀、交給它收。匯入寫完就換成重讀；批次作業裡的重讀不碰階段，原本的 `_loadOwnsLoading` 因此不用了。背景重讀（校驗做完、修書源做完、同步套用）不是階段：不鎖任何東西，誰是最新一次照讀取的序號定。

**不收進階段的**（會和階段同時成立）：

- 正在改的那幾列（`_pendingSourceMutations`）：一次可以好幾列，和閒著、重讀同時成立（刪一個書源之後的重讀）。
- `_syncReloadPending`：同步的重讀排著、等頁面露出來，任何階段都可能；它只把連續的通知併成一次。
- `_disposed`、`_listeningSync`：物件放掉了、有沒有在聽同步。
- 校驗中（`checkService.isChecking`）：校驗服務的，背景工作也會校驗。
- 頁面的 `_isImporting`：整段匯入流程（選檔、抓網址、預覽面板開著）；預覽面板開著時書源管理其實閒著，背景重讀照常，不是同一段。

**維持現狀、等使用者看圖選的**：

- 重讀與併重複書源時列看起來能按、按了不理。讓列也灰掉會在每次刪一個書源、從編輯頁回來時整份清單閃一下（#33 修過切開關時所有開關變淡）。
- 背景重讀開始併重複書源時不重畫：選單、多選工具列看起來能按，按了不理。開始併就重畫會讓它們在併的那一下灰掉。

**查到並修掉的**：

- 併重複書源時開始的背景重讀（校驗做完、修書源做完、同步套用）不等合併、直接讀：放出併之前的清單、收掉第一次讀的骨架，併完的那一次又因為不是最新一次而丟掉結果，清單留著已經刪掉的重複書源。原因是有合併在跑時就跳過、照讀；改成等它併完再讀。
- 併重複書源時切開關、刪一個書源照做：切了要留下的那個的開關，合併存回它時可能蓋掉；刪掉要留下的那個時那組不併，或書剛搬過去它就被刪。原因是能不能改一列沒看併重複書源。
- 預覽面板開著時書源管理才忙起來（背景工作開始校驗、背景重讀併重複書源），按了匯入提示「未匯入有效書源」；改成「匯入失敗：書源管理正在改書源，等它做完再匯入」。
- Codex 審查找到、改前就有的：等合併的重讀等完只重讀、不併同步新帶進來的重複書源；讀的途中合併跑完，照樣放出併之前的清單；開始併的那次被較新的蓋過時，合併出錯沒有紀錄。改成記下併完過幾次，讀的期間有合併跑過就等它併完重讀，之後照常判斷要不要併；開始併的那次記下錯誤。

換結構時自己弄出、合併前修掉的（Codex 審查找到）：批次作業自己的重讀被背景重讀蓋過時，批次作業一做完就放開清單，選單在還留著已刪書源的清單上能按；匯入寫進去時背景工作在跑、匯入自己沒併，之後的重讀也不併。前者改成交給最新一次讀清單收，後者改成匯入寫完就換成重讀。

**改後**：

| 改前 | 改後 |
|---|---|
| `_isLoading`、`_loadOwnsLoading`、`_isBatchOperationInProgress` | `_ListWork`：第一次讀、閒著、重讀、匯入、批次作業；占著的由自己收 |
| `_mergingDuplicates` | `_merging`：正在跑的那次合併，加上併完過幾次（`_mergesDone`）；讀的期間有合併跑過就等它併完重讀，能不能併只在 `_canMerge` 一處判斷 |
| （新） | `_settledGeneration`：最新一次讀清單收尾時的序號；匯入、批次作業做完時看它，較新的重讀還沒讀完就交給它收 |
| `_syncReloadPending` | 照舊（理由見上） |

`isLoading`、`isMutationBusy`、`isSourceLocked`、`canReorder` 照舊對外，都從階段與 `_merging` 算；拿掉沒人讀的 `isBatchOperationInProgress`。讀者看不到的差別：批次作業裡的重讀不再算載入中（清單有書源，骨架與「刪光時結束多選」都看不出）。

### 有聲書播放器

ADR 0055 的播放器（`lib/features/audiobook/audiobook_player.dart`），讀它的是播放器頁、收聽圓鈕與系統播放資訊。

**改前**（2026-11-20，`beta` `660b61a1`）：

| 旗標 | 意思 | 誰設 |
|---|---|---|
| `_playing` | 引擎回報在播 | 引擎的 `playingStream`；換集失敗、播放出錯、停止時直接設 false |
| `_loading` | 開書或換集中 | 開書、換集開始時 true，載完或失敗時 false |
| `_buffering` | 引擎在等資料 | 引擎的 `bufferingStream`；停止時 false |
| `_ended` | 最後一集播完 | 播完沒有下一集時 true，開書、換集時 false |
| `_error` | 最後一次失敗的原因 | 開書失敗、換集失敗、播放途中出錯 |
| `_wantPlay` | 使用者要不要出聲 | 播放、換集 true；暫停、失敗、停止 false |
| `_generation` | 哪一次載入還有效 | 開書、換集、停止、放掉時加一 |

階段散在組合裡：「打不開」是 `_chapters.isEmpty && _error != null`（播放器頁與 `open()` 各寫一次），「這一集播不出來」是有目錄又有 `_error`，「真的在出聲」是 `_playing && !_buffering && !_loading`，「回到前景可以接另一台的進度」是 `!_playing && !_loading && _chapters.isNotEmpty`。播放鍵、系統的播放鍵與收聽圓鈕都走 `toggle()`，它只看 `_playing`；載入中 `_playing` 是 false，按下去照「暫停中按播放」讓引擎播，播的是還沒換掉的上一集。

**歷史上因此出錯的**：

- #327 審查：載入中按暫停，載入完仍自己開始播（只有 `_loading`，沒記使用者要不要出聲，加了 `_wantPlay`）。
- #327 審查：收聽計時與定時在緩衝時照算（定時只看 `_playing`，沒看 `_buffering`）。
- #327 審查：換到抓不到的一集時畫面停在新集、耳朵還聽著舊集（換集失敗只設 `_error`，引擎照播）。
- #327：上次連目錄都沒開成，再開同一本不會重開（「打不開」沒有自己的狀態，加了 `_chapters.isEmpty && _error != null`）。
- #436：開書還在讀目錄、或目錄沒讀成時，「上一集」讀空清單丟錯、播放鈕畫成錯誤方塊；列表循環時「下一集」照樣亮著、按了卡在載入中；按播放、回到前景接進度也丟錯（「開書中」「打不開」只用空目錄表示，集數卻已經是上次那集）。審查另外留下沒修的一件：載入中按播放，引擎先接著播上一本停下的那一集。

查過不算：#345 把「記下書源」移到抓目錄之前（失敗畫面才給得出登入），是順序，和旗標無關；#327 的「從目錄點正在播的那集沒從頭播」是集數比較。

**階段表**（照 ADR 0055 與 `docs/design/audiobook.md` 定）。按鍵怎麼走：播放器底部膠囊的播放鍵與收聽圓鈕走 `toggle()`（播著就暫停，其他就播放）；系統的播放鍵照交出去的狀態叫播放或暫停；系統的拖動、倒退、快轉和進度條一樣走拖動。「現在一樣嗎」比的是換結構前的程式：

| 階段 | 播放器頁 | 收聽圓鈕 | 系統播放資訊 | 可以走到 | 現在一樣嗎 |
|---|---|---|---|---|---|
| 沒有書 | 還沒開這本：清單是骨架 | 收起 | 收掉 | 開書中 | 一樣 |
| 開書中（讀書源、目錄與上次聽到哪） | 清單是骨架，播放鍵轉圈 | 播放圖示 | 不動（上一本停止時已收掉） | 載入這一集、打不開、沒有書、開書中（開別本） | 不一樣：按播放鍵時，播過別本的引擎會先出聲（播的是停掉的上一本） |
| 打不開 | 清單的位置是「有聲書打不開」、原因與「重試」（要登入或驗證時是「登入」「前往驗證」） | 播放圖示 | 不動 | 開書中（重試、按播放、再開同一本）、沒有書 | 不一樣：按播放鍵、點圓鈕沒反應 |
| 載入這一集（找下載好的檔、抓網址、開音訊） | 清單，播放鍵轉圈 | 播放圖示 | 抓網址時停在上一集、暫停；開音訊時引擎回報等資料或總長，換成這一集、等資料（第一次開書時還沒有） | 播著或暫停（載好，照使用者最後要不要出聲）、這一集播不出來、載入這一集（換別集）、沒有書 | 不一樣：按播放鍵時引擎接著播還沒換掉的上一集；拖動拖的是上一集、位置記到這一集；上一集晚到的錯讓這一集播不出來 |
| 播著 | 暫停圖示；緩衝時轉圈 | 暫停圖示 | 播放中；緩衝時寫等資料 | 暫停、載入這一集（換集、播完接下一集）、播完、這一集播不出來、沒有書 | 不一樣：單集循環（與隨機只剩這一集）播完重播前，存進度的那一下按暫停、換集或停止，舊的這一集照樣出聲 |
| 暫停 | 播放圖示；緩衝時轉圈 | 播放圖示 | 暫停，停在哪 | 播著、載入這一集（換集、回到前景接另一台的進度）、這一集播不出來、沒有書 | 不一樣：回到前景接進度的途中按了播放，接進度蓋掉這次播放、停著不播 |
| 這一集播不出來 | 清單照舊，跳一則提示寫原因（要登入或驗證時旁邊給那一顆），播放圖示 | 播放圖示 | 暫停 | 載入這一集（按播放重載、換集、回到前景接進度）、沒有書 | 一樣 |
| 播完（最後一集播完，播完停） | 播放圖示，進度在結尾 | 播放圖示 | 暫停 | 暫停（拖動）、載入這一集（按播放從這一集開頭、換集、回到前景接進度）、沒有書 | 不一樣：拖進度條之後按播放，還是從開頭播 |

改後「不一樣」的那幾格照這樣做：開書中與載入這一集按播放只記下要出聲，載好照最後的意思播不播；這兩個階段拖動不做事、引擎送來的錯不算這一集的；打不開時按播放就是重試；叫引擎出聲的地方都先看使用者還要不要出聲、還是不是這一集；回到前景接進度時抓的途中按過什麼就不跳；播完後一拖就回到暫停、停在拖到的地方。

**刻意維持現狀的畫面**：載入中播放鍵轉圈、圓鈕與系統播放資訊是播放圖示，所以載入中沒有地方按暫停（只有別的播放接手時會暫停）。要改成載入中照「要不要出聲」畫暫停圖示、按了就不播，得看圖選，這次不動。

另一處：開書中、載入這一集時拖動不做事之後，播放器的進度條與倒退、快轉 10 秒照 ADR 0059 該灰掉，現在仍亮著、按了沒反應。灰掉要看圖選，這次不動。

**不收進階段的**（會和階段同時成立）：

- 緩衝（`_buffering`）：引擎回報在等資料，播著與暫停時都可能（暫停中拖動也會等資料）；播放鍵轉圈、系統播放資訊寫等資料、收聽時間與定時不算。
- 使用者要不要出聲（`_wantPlay`）：每次載入開始時定下（換集、重播是要，接另一台的進度是不要，開書、播完接下一集照當時的意思），載入途中按的播放或暫停蓋過它，載好只看它；暫停時在接手系統播放的那一下也看它。別的播放接手、定時到了都只改它。
- 哪一次載入還有效（`_generation`）：每次開書、換集、停止加一，每個等待之後拿它比，比不上就是被後來的動作取代了；階段相同時也要分得出是哪一次（例如兩次換集都在載入這一集）。
- 使用者按過幾次（`_commands`）：開書、播放、暫停、拖動、換集、停止各加一（含系統的按鍵與定時到了）。回到前景接另一台的進度要知道抓的途中有沒有按過什麼；按了播放還在等系統接手時，階段、集數與位置都還沒變，看不出來。

**重構時查到並修掉的**（表上寫「不一樣」的格子與 Codex 審查找到的，各一個提交，先寫會失敗的測試）：

- 載入中（開書中、載入這一集）按播放鍵、收聽圓鈕或系統的播放鍵，引擎先接著播還沒換掉的上一集（或停掉的上一本）。原因是 `play()` 只分「失敗或播完」與「其他」，載入中落進「暫停中按播放」。
- 單集循環（與隨機只剩這一集）播完重播前，存進度的那一下按暫停（含定時到了、別的播放接手）、換集或停止，舊的這一集照樣出聲。原因是重播直接叫引擎播，沒經過看「還要不要出聲」的那道關。
- 最後一集播完後拖進度條再按播放，還是從開頭播；引擎還沒拖好就按播放也是。原因是 `_ended` 只在開書、換集時清掉，拖動不會。
- 整本打不開時按播放鍵、點收聽圓鈕沒反應。原因是第一次開書就失敗時沒有引擎、直接返回；播過別本時重載這一集又因為沒有目錄不做事。
- 回到前景接另一台的進度時，抓的途中按了播放（重載播不出來的那一集，或還在等系統接手），抓回來照樣跳過去、蓋掉這次播放、停著不播，還記成同步過。原因是抓回來後只用 `_playing`、集數與位置猜有沒有按過，這兩種情況三樣都還沒變。
- 載入途中按的播放或暫停被蓋掉：接另一台的進度時按播放，載好仍停著；開書中或按了暫停之後才報播完，開書與接下一集又把「要出聲」設回去。原因是載好播不播看「這次是不是自動播」和 `_wantPlay` 兩件同時成立。
- 換集途中（存進度、等上一集停聲）停止或開了別本，舊的換集回來讀清空的目錄丟錯，或拿新書的目錄換到同一個集數。原因是換集等完才記下「這一次」。
- 換集抓網址時拖動（含系統的），拖的是引擎裡的上一集，拖到的位置被記成新的一集聽到哪。原因是拖動只看有沒有書與引擎。
- 換集抓網址時引擎送來上一集的錯，被算成新的一集播不出來。原因是引擎的錯不分是哪一集的，任何階段都採用。

換結構前補的偵測測試有一項寫下的是最後一件的舊行為（留著原因、不播），判斷舊的是錯的，改了測試。

**改後**：

| 改前 | 改後 |
|---|---|
| `_playing`、`_loading`、`_ended`、`_error` | `AudiobookPhase`：沒有書、開書中、打不開、載入這一集、播著、暫停、這一集播不出來、播完；原因只在打不開、播不出來時有 |
| 引擎的 `playingStream` 任何時候都改 `_playing` | 只在播著與暫停之間換；載好時照引擎現在播不播定播著或暫停 |
| 引擎的錯任何階段都採用 | 開書中、載入這一集時不採用（這一集開不了由開檔丟出） |
| 三處各自叫引擎播（播放、載好自動播、單集循環重播） | 都經過 `_startPlaying`：還要出聲、還是同一次載入、這一集開好了才播 |
| 載好播不播看 `autoplay && _wantPlay` | 每次載入開始時定下 `_wantPlay`，載好只看它 |
| 拖動只看有沒有書與引擎 | 只在播著、暫停、播完、播不出來時算數；播完一拖就回到暫停 |
| 回到前景接進度用 `_playing`、集數與位置猜有沒有按過 | 看 `_commands` 有沒有變 |
| 頁面用「有沒有目錄」分打不開與播不出來 | 頁面的狀態畫面、失敗提示與重試直接讀 `phase` |
| 播放鍵、收聽圓鈕與系統播放資訊各自看 `_playing`、`_loading \|\| _buffering` | 讀 `playing`（階段是播著）與 `loading`（開書中、載入這一集，或在緩衝），兩個都只由階段加上緩衝算出 |

留成欄位的四個（`_buffering`、`_wantPlay`、`_generation`、`_commands`）見上面「不收進階段的」。

**審查看了沒改的**：單集循環重播時，真的引擎（just_audio）播完仍算在播，回到開頭那一下就會出聲，之後才經過 `_startPlaying`；這段時間按了暫停，引擎照樣停下，最後的狀態是對的，不改。

### 朗讀

閱讀器的朗讀（`lib/features/reader/features/tts/reader_tts_controller.dart`）：念哪一句、換章接著念、暫停與繼續、上一章下一章、結束，面板、定時鍵、定時與系統播放資訊都照它。

**改前**（2026-11-20，`beta` `660b61a1`）：

| 欄位 | 意思 |
|---|---|
| `_speechGeneration` | 每次開始、暫停、跳章、結束、正文換了就加一；載入與念完回來比對，不同就作廢 |
| `_completionGeneration` | 正在處理哪一輪的念完，同一輪的下一個念完不理 |
| `_skipTarget` | 按了上一章、下一章還在載入的那章，連同按下時的輪數；輪數對不上就當沒有 |
| `_resumeLocation` | 不是 null 就是已暫停，播放鍵從這裡接著念 |
| `_segments`、`_segmentIndex` | 這一章要念的句子與念到哪一句；`-1` 是沒有在念的句子 |
| `_speechStartLocation` | 正在念的那句開頭；沒有人讀 |

「正在朗讀」是 `(_skipTarget 輪數對 ?? _resumeLocation ?? 目前那句) != null && _resumeLocation == null`。「要念的那章還在載入」沒有欄位：自動換章與暫停後繼續靠上一章的句子還留著看起來在念，按上一章下一章靠 `_skipTarget`，開始念與經過空章時什麼都沒有，所以算沒在念。

**歷史上因此出錯的**：

- #320 前：句與句之間按暫停，下一句照樣開始念。原因是「已暫停」看引擎沒在發聲、還有念到一半的字，句與句之間引擎本來就停著。改成停在一句（`_resumeLocation`）。
- #320 審查：下一章還在載入時按上一章，新章念完第一句就沒聲音。原因是「正在處理念完」是不分輪的布林值（`_handlingCompletion`），被還在等下一章的舊一輪佔著。改成記哪一輪（`_completionGeneration`）。
- #320 審查：快速連按兩次下一章只前進一章，第二次還從沒換掉的舊章算。加了 `_skipTarget`。
- #362 審查：換章載入中或兩句之間，面板與定時鍵當成沒在念、從畫面重念。原因是「正在朗讀」看引擎有沒有在發聲。改看上面那串欄位。

**階段表**（讀者看到的，照 `docs/design/reader.md`「朗讀」）：

| 階段 | 讀者看到什麼 | 可以走到 | 現在一樣嗎 |
|---|---|---|---|
| 沒在朗讀 | 面板「開始朗讀」、定時鍵「定時朗讀」；沒有高亮、沒有系統播放資訊；音量鍵翻頁 | 朗讀中（載入畫面這一頁那章） | 一樣 |
| 朗讀中：載入那一章 | 面板與定時鍵「暫停朗讀」，倒數在走；系統播放資訊是要載入的那一章、在播；高亮留在剛念的那句；音量鍵調音量 | 念一句；載入下一個有正文的章（這章沒有可念的字）；已暫停（停在要載入的位置）；載入上一章、下一章（從要載入的這章算）、手動跳到的新位置；沒在朗讀（結束、載入失敗、念到書尾、正文換了） | 不一樣，見下面 |
| 朗讀中：念一句 | 同上，高亮是正在念的那句，系統播放資訊是那句的章 | 念下一句；載入下一章（跳過付費章節）；已暫停（停在這句開頭，引擎沒念出來時也是）；載入上一章、下一章、手動跳到的新位置；沒在朗讀 | 不一樣：引擎沒念出來時改前一直停在這裡、手動跳轉改前先結束再重來（下面審查修掉的） |
| 已暫停 | 面板與定時鍵「繼續朗讀」，倒數停住；系統播放資訊留著、顯示暫停（另一方開始播時交出去）；高亮留在停的那句 | 朗讀中（載入停的位置）；載入上一章、下一章（暫停中按了也開始念）；沒在朗讀（結束、手動跳到別處、正文換了）；再收到暫停時不動 | 不一樣：再收到暫停時停的位置會改回剛念的那句（下面查到的 bug） |

讀者分得出的是三個：沒在朗讀、朗讀中、已暫停，面板與定時鍵直接讀這三個。載入那一章和念一句讀者看起來一樣，分開是因為念完一段只在念一句時算數。

「載入那一章」改前五種進法各不一樣（探測：章節載入卡住時看讀者拿到什麼），改成同一套：載入中的那一章就是要念的那章，進入載入就算朗讀中。

| 怎麼進來 | 改前 | 改後 |
|---|---|---|
| 開始念 | 算沒在念：面板仍寫「開始朗讀」、沒有系統播放資訊、倒數沒開始；按暫停沒反應，載入好照樣開始念；手動跳到別處後仍念舊位置 | 朗讀中；暫停停在要念的位置；手動跳轉從新位置念 |
| 念完一章自動換章 | 系統播放資訊還是舊章；按暫停停在舊章最後一句，繼續時把念完的那句再念一次；按下一章從舊章算 | 系統播放資訊是要念的章；暫停停在那章開頭；下一章從那章算 |
| 經過沒有正文的章 | 算沒在念，按暫停沒反應；系統播放資訊沒更新，還寫舊章在播；高亮消失 | 朗讀中，系統播放資訊換到要念的章；高亮留在剛念的那句 |
| 按上一章、下一章 | 一樣，只有引擎補報的念完會念出舊章的下一句 | 補報的念完不理 |
| 暫停後繼續 | 載入好之前系統播放資訊仍顯示暫停；載入中到的補報念完會讓它多念一句 | 一按就顯示在播；載入中到的補報念完不理 |

開始念時就交出系統播放資訊：另一方（有聲書）照 ADR 0055 在按下開始的那一刻暫停，不等章節載入好；按上一章下一章本來就是這樣。

**重構時查到並修掉的**：

- 念完一章、下一章沒有正文時往後找，沒跳過付費章節，碰到付費章節就提示「第 N 章無法載入，朗讀已結束」。原因是往後找直接加一，念完一章時用的「下一章」才有跳過付費章節。一處邏輯錯，先在舊結構上修。
- 按了上一章、下一章、那章還在載入時，引擎補報的念完念出舊章的下一句。原因是 `_skipTarget` 輪數對、舊句子還在，念完照樣往下。新結構念完只在念一句時算數，寫不出來。
- 上表「載入那一章」四種進法的差別：開始念與經過空章時暫停沒反應、自動換章暫停後重念念完的句子、系統播放資訊停在舊章。原因是載入中沒有欄位，靠舊句子還在推出來。
- 暫停中打開有聲書（另一方開始播，朗讀收到暫停）：停在按了上一章下一章或自動換章那章開頭的，停的位置被改回剛念的舊句，繼續時重念舊章。原因是暫停照「剛念的那句」重算停的位置，沒看已經暫停。

合併前 Codex 審查找到、修掉的：

- 改前就有：朗讀中手動跳轉、等引擎停好時按結束，等完照樣念，跳轉也讓定時重新倒數（改成和上一章下一章同一套，直接換到新位置的載入）；結束後馬上開始，定時沿用上一輪剩下的（結束當下就通知）；引擎出錯、不收這句或沒開好時一直停在朗讀中卻沒聲音（朗讀服務多送 `failures`，收到就停在這句並提示「朗讀引擎出錯，已暫停」）；系統播放資訊的上一章、下一章在只剩付費章節的方向仍顯示、按了沒反應；經過沒有正文的章時高亮消失。
- 兩個自己定的：引擎沒念出來時暫停、不結束，位置留著，一時出錯按繼續就能接著念，完全沒有引擎時每按一次提示一次；朗讀中手動跳轉時倒數照走，跳轉是「從新位置接著念」，不是重新開始朗讀（`docs/design/reader.md`「定時」只在每次開始時重新倒數）。
- 這條分支擴大或弄出的：還沒載入的章在系統播放資訊上用沒轉換繁簡的章名（一進載入就換到要念的章後，碰得到的情況變多）；開始念、章節還沒載入就暫停後開自動翻頁，朗讀沒收掉（自動翻頁改看階段不是「沒在朗讀」）。

**改後**：

| 改前 | 改後 |
|---|---|
| 7 個欄位拼出現在在哪 | 一個 `_TtsState`：`_Idle`、`_Loading`（要念的位置、剛念的那句）、`_Speaking`（這章的句子、第幾句）、`_Paused`（停的位置、停的那句） |
| 面板與選單讀 `isPlaying`、`isPaused` 兩個布林值拼出播放列的字 | 讀 `ReaderTtsPhase`：沒在朗讀、朗讀中、已暫停；`isPlaying` 留著當判斷函式（音量鍵、自動翻頁、畫面跟隨） |
| 輪數比對作廢晚到的載入與念完 | 階段物件本身：等待回來看還是不是它 |
| `_completionGeneration` 與暫停時的判斷擋念完 | 念完只在 `_Speaking` 時算數 |
| 引擎沒念出來時沒有消息 | 朗讀服務的 `failures`：念一句時收到就停在這句、提示 |

改後寫不出來的組合：已暫停又有按下的章在載入（改前 `_resumeLocation` 與 `_skipTarget` 可以同時有值）；算沒在念卻有系統播放資訊在播（經過空章時）；載入中卻沒有要念的那章。

改測試一處（舊規則寫進了期望）：自動換到第三章載入中按上一章，原本期望念第一章（從舊章算），現在念第二章（從載入中的第三章算，和系統播放資訊寫的一致）；這項測試要驗的「新一輪念完一句接著念」（#320）照舊驗。

順手改的：拿掉沒有人讀的 `speechStartLocation`。

沒有測試蓋到的：正文換了（排版、替換規則重載）時停下朗讀，要真的換一版正文才觸發，這次沒補。

**不收進階段的**：

- `_disposed`：放掉了，任何階段都可能；放掉後不再通知。
- `_observedContentGeneration`：上次看到的正文版本，是閱讀器的計數，用來分出這次通知是不是正文換了。
- `_chapterTitles`：念過的章的章名快取，系統播放資訊的標題用。
- 作廢晚到的載入與念完：每次進入載入或念一句都是新的一個階段，等待回來時看現在還是不是它，不另記輪數。
- 念著時引擎連報兩次念完：第二次照樣往下一句（改前在處理第一次的期間不理）。分不出是真的念完還是重複，真的念完不能不理，否則會停住。

| 目錄沒抓到 | 「目前來源目錄載入失敗，建議換源後再試」；蓋過書籍資訊沒更新到 | 重新載入、檢查更新、換源；加入書架或預下載時重抓到目錄就收掉 | 不一樣：重抓到目錄（加入書架、預下載、檢查更新）後那一列還在；從書源編輯、除錯頁回來就不見了，目錄其實還是空的 |
| 目錄要登入 | 「目錄需要登入後閱讀」與「登入」，點了去登入，登入資料變了就重新載入；只在書源有登入時 | 同上 | 同上兩項，另加：重抓到目錄後「登入」先消失、字還在 |

進行中的操作（檢查更新、換源、加入或移出書架）：

| 操作 | 讀者看到什麼 | 再按一次 | 現在一樣嗎 |
|---|---|---|---|
| 檢查更新 | 選單「正在檢查更新…」灰掉，做完跳提示 | 回「正在檢查更新」 | 一樣 |
| 換源 | 換源面板的狀態列「正在切換來源…」、清單不能點（面板自己記，屬於搜尋那個候選），成功時面板關掉 | 回「正在換源，請稍候」（面板擋住了，讀者按不到） | 一樣 |
| 加入或移出書架 | 按鈕馬上變成新的樣子，失敗變回去 | 回「正在更新書架，請稍候」；移出的確認框不再跳出 | 一樣 |

**重構時查到並修掉的**（各一個提交，先寫會失敗的測試；最後兩件是 Codex 審查找到的）：

- 目錄沒抓到的書，加入書架、預下載或檢查更新時重抓到了目錄，那一列還寫「目前來源目錄載入失敗，建議換源後再試」。原因是抓到目錄只把 `_loginRequired` 設回 false，沒動同一列的字串。
- 同上，要登入的那種：「登入」先消失，「目錄需要登入後閱讀」的字還在。同一個原因，同一個提交。
- 目錄要登入之後從書源編輯頁回來、書源已經不能讀：那一列換成健康說明，「登入」還掛在旁邊。原因是字串換了、`_loginRequired` 另記沒跟著換。
- 目錄要登入或沒抓到、書籍資訊沒更新到時，從書源編輯或除錯頁回來，那一列就不見了，目錄其實還是空的。原因是書源的健康說明和抓書源的結果擠在同一個字串，重讀書源只能整列換掉。
- 這頁目錄要登入，閱讀器或書架另外把目錄存進手機：加入書架、預下載直接用存著的目錄，那一列還在。原因是目錄的問題只在抓目錄的那幾處設、清，沒照手上的目錄算。
- 加入書架重抓目錄時按了檢查更新，檢查更新先帶回目錄、重抓較晚才失敗：那一列又設回來，畫面同時有目錄與「目錄載入失敗」。原因同上。

**改後**：

| 位置 | 改後 |
|---|---|
| 載入 | `BookDetailWorldState`：載入中、可以操作、載入失敗；錯誤訊息照它算 |
| 書源問題那一列 | 書源不能讀照手上書源的健康狀態算，不記；`_FetchIssue`：沒問題、書籍資訊沒更新到、目錄沒抓到、目錄擋在登入牆後。`sourceIssueMessage`、`loginRequired` 在顯示時照這兩件與手上的目錄、書源算：健康說明蓋過抓書源的結果；目錄的問題只在手上的目錄還是空的時候寫；登入牆只在書源有登入時寫成「目錄需要登入後閱讀」與「登入」，沒有就寫目錄沒抓到 |
| 進行中的操作 | `BookDetailAction`（檢查更新、換源、加入或移出書架）與 `_runOnce`：進行中的放在一個集合，各自擋自己，三件可以同時進行；頁面讀 `isRunning(...)` |
| 留著的 | `_disposed`（任何階段都可能；通知一律經過覆寫的 `notifyListeners` 看它）；`_switchedBookUrl`（閱讀器換了源的新網址，是資料不是階段）；目錄搜尋與排序（使用者的選擇） |
| 拿掉的 | `_isCacheStatusLoading`（沒有人讀） |

抓書源的結果什麼時候換：進頁或重新載入、閱讀器換了源、這頁換源、檢查更新成功時清掉；書籍資訊抓失敗時記成「沒更新到」（已經有目錄的問題時不蓋），抓到時收掉；目錄抓失敗時記成「沒抓到」或「擋在登入牆後」。目錄後來有了不用另外清，顯示時就不寫。重讀書源不動它。預下載、檢查更新因為書源不能讀被擋時，理由只看書源本身。

讀者看得到的差別是上面的 bug；另外換源換到的書源本身不能讀時那一列改寫它的健康說明（原本不寫），只在換源清單列出之後書源才變成不能讀時碰得到。偵測測試沒有改到期待值，只把讀「檢查更新中」「更新書架中」的兩處換成 `isRunning(...)`。

換結構時自己弄出、合併前修掉的（Codex 審查找到）：重讀書源改成保留抓書源的結果之後，書源拿掉登入或被刪掉，那一列還掛「登入」；書源停用後預下載、檢查更新的被擋理由寫成舊的目錄提示；重抓回零章時當成抓到、那一列收掉。同一次審查找到改前就有的兩件（上面清單最後兩件），一起修了。

查過、沒修的：檢查更新途中書被移出書架或換了源，更新服務略過寫回、回報成功，詳情照成功收掉「書籍資訊更新失敗」；要更新服務另外回報「略過」才分得出來，碰到的時機很窄，留著。

### 同步

`lib/core/sync/sync_service.dart` 決定什麼時候跑哪一種同步（ADR 0039、0046）：日常只同步閱讀進度，「立即全面同步」與剛選好同步空間時同步全部種類；同一時間只跑一段，途中又有人要就排著，跑完再補；全面同步可以取消，在兩種資料之間停。

**改前**（2026-11-20，`beta` `660b61a1`）：

| 旗標 | 意思 | 什麼時候成立 |
|---|---|---|
| `_running`（`Future?`） | 有一段同步在跑（含途中補跑的輪次） | 從要求到最後一輪做完；`_finishRun` 掛在 `whenComplete` 上放下 |
| `_again` | 跑的途中又有人要同步 | 只在跑的時候設；每輪開始清掉 |
| `_fullPending` | 有人要全面同步、那一輪還沒開始 | 跑的時候和 `_again` 一起設；閒著時要求的，第一輪開始前就取走 |
| `_cancelled` | 使用者取消了這一輪全面同步 | 按了取消到下一輪開始；進度輪裡按也會設，只是沒作用 |
| `_progressFirst` | 有人要閱讀進度插隊先送 | 離開閱讀器、有聲書存進度時設；做進度那一種時清掉 |
| `_authorizingGoogleDrive` | Google 登入畫面開著 | 選 Google 雲端硬碟的那段；這段期間回到前景、退到背景都不同步 |

「這一輪是全面同步」只活在 `_runUntilSettled` 的區域變數，「排著的是全面同步還是進度」要看 `_again` 與 `_fullPending` 兩個一起；取消把 `_fullPending` 清掉、`_again` 留著，排著的全面同步就變成一輪進度同步。進度框按下取消後的「正在停下…」與收掉後那行提示，是進度框自己記的「按過取消」加上整段跑完後的 `status.error` 拼出來的，不是服務告訴它的。

**歷史上因此出錯的**（`git log -G'bool _旗標名'` 找到的都是加旗標的那個功能或修正：#194 `_again`、#232 `_authorizingGoogleDrive`、#235 `_progressFirst`、#257 `_fullPending` 與 `_cancelled`；之後動到這幾個旗標的提交只有 #199、#208 改收尾，打開 diff 都不是修旗標組合）：

- #257 審查：「同步結束」的通知裡又要求全面同步，拿到的是剛結束那一段的 future，要求的全面同步沒跑。原因是狀態已經寫成結束、`_running` 還沒放下；改成先放下再通知。

查過不算：#232 審查的「補跑的輪次之間 `running` 不閃成 false」是補測試，當時的程式沒錯。

**階段表**（讀者看到的，照 ADR 0046 與 `docs/design/screens.md`「備份與同步」定）：

| 階段 | 讀者看到什麼 | 可以走到 | 現在一樣嗎 |
|---|---|---|---|
| 閒著 | 「立即全面同步」的副標是上次全面同步的時間或失敗原因；沒有進度框 | 同步進度、全面同步 | 一樣 |
| 同步進度 | 副標「同步中（1/1）：閱讀進度」；開 App、回到前景時開書等它做完進度那一步 | 閒著；排著的是進度或全面時，直接進那一輪 | 一樣 |
| 全面同步 | 進度框「全面同步中」、進度條與正在同步哪一種、「取消」；副標同上 | 停下中、閒著；排著的是進度或全面時，直接進那一輪 | 一樣 |
| 停下中 | 進度框「正在停下…」灰掉；手上這一種做完就停，寫完的留著 | 閒著；排著的是進度（取消降成的）或取消之後才要求的全面時，直接進那一輪 | 不一樣：最後一種做著時按取消，其實全部做完、上次全面同步的時間也更新了，提示卻寫「已停下」 |

輪與輪之間直接換，中間不經過閒著、也不通知閒著。`status.phase` 在下一輪拿到同步空間、真的開始前，還是上一輪的階段。

**排著的下一輪**（跑的途中又有人要，和上面的階段同時成立，另記）：沒有、同步進度、全面同步。同時要過進度與全面同步時排全面同步，它含進度。取消把排著的全面同步降成同步進度：排的時候可能也有人要過進度（退到背景、有聲書存好進度），分不出來就照要過算，不漏送。

| 排著 | 讀者看到什麼 | 現在一樣嗎 |
|---|---|---|
| 全面同步排在日常同步後面 | 進度框已經開著，寫「全面同步中」與日常那一輪的進度；按取消就不跑 | 不一樣：取消後要等日常那一輪、再加一輪補跑的進度同步做完，進度框才收 |
| 同步進度排在全面同步後面 | 進度框照全面那一輪走 | 不一樣：全面那一輪做完，還要等補跑的進度輪做完才收；ADR 0046 只要求至少等到全面那一輪 |

**進度框收掉後那一行**照這次要求的那一輪全面同步怎麼結束：做完是「全面同步完成」，取消停下是「已停下，同步好的資料留著」，失敗是「全面同步失敗：原因」。現在不一樣：那一行是進度框自己記的「按過取消」加上整段跑完後的 `status.error` 拼的，所以除了上面「停下中」那件，還有三種會寫錯：

- 全面那一輪有一份檔被拒絕，補跑的進度輪成功、把錯清掉，寫成「全面同步完成」。
- 全面那一輪成功，補跑的進度輪失敗，寫成「全面同步失敗」。
- 之前日常同步留下的錯還在，這次全面同步取消了（取消不清錯），寫成「全面同步失敗：舊原因」。

**不收進階段的**（會和階段同時成立）：

- `_progressFirst`：閱讀進度插隊，在全面同步或停下中的任何一種做完後都可能成立。收進跑著的那一段同步裡，整段做完就跟著放掉，閒著時不會留著。
- `_authorizingGoogleDrive`：Google 登入畫面開著，和有沒有在同步無關（登入時日常同步可能正在跑）。選同步空間那頁在登入中把按鈕停用，不會疊兩次。
- `_progressPending`：開書在等進度那一步，跟著開 App 與回到前景，和哪一輪無關。
- 「有一段在跑」和「讀者看到同步中」不是同一件事：沒設同步空間時一段同步照樣跑完（什麼都不做），副標不寫同步中。

**重構時查到並修掉的**：

- 進度框要等整段同步做完才收：全面同步途中退到背景、有聲書存好進度排了一輪進度同步，全面那一輪做完還要等它；全面同步排在日常同步後面時按取消，也要等日常那一輪再加一輪補跑。原因是 `syncAll()` 傳回的是整段的 `_running`，不是自己那一輪。
- 回到 App 時開書可能等到前一輪的進度（Codex 審查找到，改前就有）：退到背景或開 App 的那一輪還在讀雲端時回到 App，前一輪做完進度就放掉回來時的等待，開書照回來之前的雲端開、晚到的進度也不接；「同步結束」的通知裡回到 App 的，收尾接著把新的等待放掉。原因是開書的等待是一個共用的值，任何一個進度步驟或收尾都放它，沒記是哪一次要求的。
- 全面同步做到 AI 找書（ADR 0060）那一種時，進度寫「資料」：種類名稱的對照漏了它（Codex 審查找到，改前就有）。
- 進度框收掉後那一行是進度框自己拼的（「按過取消」加整段跑完後的 `status.error`），四種寫錯：
  - 最後一種做著時按取消：其實全部做完、上次全面同步的時間也更新了，卻寫「已停下」。
  - 全面那一輪有一份檔被拒絕、補跑的進度輪成功把錯清掉：寫成「全面同步完成」。
  - 全面那一輪成功、補跑的進度輪失敗：寫成「全面同步失敗」。
  - 之前日常同步留下的錯還在、這次取消了：寫成「全面同步失敗：舊原因」。

**改後**：

| 位置 | 改後 |
|---|---|
| `lib/core/sync/sync_service.dart` | `SyncPhase`：閒著、同步進度、全面同步、停下中。`_SyncRun`（null 就是閒著）記這一輪的階段、排著的下一輪（沒有、進度、全面）、進度插隊，與等這一輪和排著那一輪全面同步結果的人 |
| `SyncStatus` | `running` 換成 `phase`，`running` 由它算出；只在有同步空間、這一輪真的開始時寫成同步中 |
| 開書等待（`progressReady`） | 進度那一步開始時記下當時在等的那一個，做完只放它；回到前景換新的等待，舊的跟著新的放；整段收尾先取下這一段的等待再通知 |
| `syncAll()` | 傳回要的那一輪全面同步的 `FullSyncResult`（做完、停下、失敗與原因）；排著時取消就馬上傳回停下 |
| 進度框 `lib/features/settings/full_sync_dialog.dart` | 「正在停下…」讀 `phase`，收掉後那一行讀結果，不再自己記取消 |

最後一次看排隊和放下 `_SyncRun` 在同一段同步程式裡（改前放下掛在 `whenComplete` 上），先閒著再通知照舊，#257 那件寫不出來。讀者看得到的差別只有上面修掉的幾件：進度框在全面那一輪做完（或排著時取消）就收，收掉後那一行照那一輪的結果寫。

換結構時自己弄出、合併前修掉的（Codex 審查找到）：取消先發布「停下中」才把排著的全面同步降級，聽到通知才要求的全面同步會被同一次取消吃掉。總耗時的日誌原本在最後一次看排隊和放下之間，一起移到放下之後（日誌委派只有書源 isolate 會設，同步服務碰不到）。

查過不修：兩個全面同步進度框疊在一起時，先做完的那個 `pop` 會關掉上面那個。進度框有遮罩、按返回關不掉，正式的三個入口（立即全面同步、選好 Google 雲端硬碟、存好 WebDAV）疊不出兩個框，改前也是同樣的 `pop`。

改測試的兩處：排著時取消的偵測測試，進度框原本等日常那一輪做完才收，現在馬上收；插隊送進度的測試，A 的全面同步做完時補跑的那一輪還在跑，B 要等它做完才開始。

「這次搜尋在哪一段」散在四個布林值：送出後還在存紀錄是 `_pending && isSearching`，照條件搜是 `_choosing` 到選好書源為止，重試是 `_retrying`，讀回還沒合併是 `_unmerged`；暫停是 `isSearching` 留著、等 `markPaused` 才放下。頁面再把搜尋頁與背景那件的旗標拼成畫面：進度那一列與頁首「結束」看 `isSearching || isBackgroundPaused`（四處），「暫停」看 `isInBackground && !isBackgroundPausing && !isBackgroundStopping`，文字照 `isBackgroundPausing`、`isBackgroundStopping`、`isBackgroundPaused` 的先後挑。

**歷史上因此出錯的**：

- #30：送出搜尋到引擎真正開始（存紀錄、讀書源清單）這段，`_isSearching` 還沒立起來，閃出「尚未加入可搜尋的書源」，也擋不住重複送出。原因是少了「送出了、還沒開始」這一段，之後補成先立 `_isSearching`。
- #433 審查（提交 `b21d73ec9b`）：還在存搜尋紀錄就放到背景、暫停或結束，存完照樣把書源全送出去。原因同上：那一段沒有名字，補了 `_pending` 與號碼。
- #433 審查（同一個提交）：正在暫停時按結束停成已暫停。原因是 `_pausing`、`_ending` 兩個布林值，收成 `_Settling`（#458 再換成 `WorkPhase`）。
- #444 審查（提交 `47c5fb74a4`）：重試讀書源那段空檔就立著 `_retrying`，這時開始的新搜尋算不到自己的書源總數（失敗那一列「共 N 個」停在上一次的）。改成只包住真正在重試的那段。

查過不算：#442（#437）接回後換類別照舊類別搜，是先組條件、才離開接回的那一次的先後問題，不是旗標組合；#444 其他幾項是條件與範圍怎麼定。

**階段表**（讀者看到的，照 ADR 0070、`docs/design/screens.md`「放到背景」與 `components.md`「狀態用詞」定）。搜尋頁的進度那一列、頁首「結束」與頁首下緣的進度條只讀這一個階段（`SearchStage`）；結果怎麼列、空狀態寫什麼照關鍵字與結果，不是階段：

| 階段 | 讀者看到什麼 | 可以走到 | 現在一樣嗎 |
|---|---|---|---|
| 沒在搜 | 還沒搜過是搜尋紀錄；搜過是結果與結果工具列（或空狀態），頁首「搜尋」 | 搜尋中 | 一樣 |
| 搜尋中（搜尋頁自己的） | 進度那一列「正在搜尋 124/396」（剩不到三個時「還在等：…」）與「放到背景」（別的背景工作在跑時灰掉）；頁首紅字「結束」 | 沒在搜（搜完、按結束）、放到背景做著 | 一樣 |
| 放到背景做著 | 進度那一列同上，右邊「暫停」；通知欄同一句 | 正在暫停、正在結束、沒在搜（搜完） | 一樣 |
| 正在暫停 | 進度那一列「正在暫停…」、不放動作；頁首「結束」還能按（結束蓋過暫停） | 已暫停、正在結束 | 不一樣：按下去頁面沒更新，還是「還在等：…」與能按的「暫停」，停好才跳成已暫停（已修，見下） |
| 已暫停 | 進度那一列「已暫停 124/396」與「繼續」（別的背景工作在跑時、讀回存檔中灰掉）；頁首「結束」 | 放到背景做著（繼續）、正在結束 | 一樣 |
| 正在結束（暫停中按結束） | 進度那一列「正在結束…」、不放動作；頁首「結束」 | 沒在搜 | 不一樣：旁邊還留著灰掉的「繼續」（已改，見下） |

做著時按結束不經過「正在結束」：搜尋本身當下就停了，頁面直接是沒在搜（結果工具列、頁首「搜尋」），結果照常能排序、篩選；背景那件還要等送出去的書源回來（不理會取消的最多等 20 秒）、寫完結束那一行才停好，這段時間只有通知欄寫「正在結束…」。頁面要不要也寫「正在結束…」等它停好（代價是這段時間沒有結果工具列）留給使用者選。

讀者看不到、收在階段裡的：

- 搜尋中、放到背景做著的「送出了、還在存搜尋紀錄」（這時按結束、暫停、開始新的一次就不送書源）、「重試失敗」（「共 N 個」照整次搜尋的書源數）、「接著搜暫停的」（進度接著數）都是一次搜尋（`SearchRun`）內部的段，畫面一樣是搜尋中。
- 放到背景按了暫停之後，搜尋本身已經停下、等結果檔寫完才算暫停好：這段是正在暫停。
- 接回放到背景的那一件、換頁還沒播完：進度那一列照那一件的階段，結果先不放、這一頁還不算看過（`_Attachment`）。讀回的結果還沒合併成卡也收在這裡。

**誰記哪一段**：一次搜尋自己記它在哪一段（還沒搜、讀回還沒合併、送出了在存紀錄、照條件搜、重試、接著搜、暫停時停下等記成已暫停），因為只有它知道每個回報屬於哪一段；暫停、結束、繼續照舊由背景那件（`RepairRun`）記；搜尋頁只記怎麼看著背景那件（還沒、接回了等進場、看著），從這兩邊算出 `SearchStage`。

**不收進階段的**（會和階段同時成立）：

- `_disposed`（三處）：物件放掉了，任何階段都可能。
- 背景那件的 `_abandoned`：接回它的搜尋頁開始了別的搜尋，和做著、已暫停、做完都能同時成立（同上一節的 `_seen`）。
- 背景那件的 `_headerWritten`：結果檔的第一行寫了沒，是檔案的事；做著時可能還沒寫（書源還沒選好），讀回的本來就有。
- 搜尋頁的 `_entered`：進場播完了沒，和每個階段都能同時成立。
- 搜尋引擎的「被整頁蓋住時暫停送出」（`SearchModel.pause`）：和搜尋中同時成立，是另一件事。
- `background`（放到背景了沒）：放到背景時設一次，之後不變，是這次搜尋的模式。

**換源跳過**：`book_detail_change_source_provider.dart` 只有一個 `isSearching`，配「第幾輪」的號碼丟掉舊一輪晚到的結果；沒有好幾個布林值互相牽動，換源面板的「正在切換來源…」（`_isSwitchingSource`）和搜尋中會同時成立。不換結構；途中查到搜尋前幾步出錯會一直轉圈，修了（見下）。

**重構時查到並修掉的**：

- 放到背景的搜尋按了暫停，通知欄換成「正在暫停…」，搜尋頁卻還是「還在等：…」與能按的「暫停」，停好才直接跳成「已暫停」。原因是暫停只停下搜尋（結果、進度都沒變，不通知）、只更新通知欄，頁面聽的兩邊都沒出聲。從 #433 起。
- 重試失敗時有書源不理會取消（網站卡住、規則跑不完），這時開始新的搜尋，新的那次失敗那一列的「共 N 個」停在上一次的。原因是重試中的 `_retrying` 要等重試那一段結束才放下，沒跟著每一次搜尋走；和 #444 審查那件同一個原因，那次只修了讀書源的空檔。
- 換源讀書源或搜尋快取出錯時，面板停在「正在初始化...」一直轉圈，原因也沒寫。出錯處理只包住送書源那一段，前面幾步的例外跳過了收尾。
- 放到背景的搜尋暫停中按結束、還在寫結束那一行時（表上「正在結束」那一列）：「正在結束…」旁邊留著灰掉的「繼續」。現在照正在暫停，不放動作。

換結構時找到、合併前修掉的（Codex 審查找到）：放到背景的搜尋搜完、還在寫結果檔時從通知按暫停，通知照樣換成「正在暫停…」，寫完又直接做完（從 #433 起）；現在搜尋已經停下就不接受暫停。正常暫停時，搜尋本身停好到背景那件存好結果檔之間，頁面一瞬間讀成沒在搜；現在正在暫停直到已暫停。

另外放寬了背景搜尋頁面測試等寫檔的時間（同一台機器上還有別的測試在跑時，約十次失敗一兩次），並改掉一項等的條件永遠不成立的暫停測試。

**改後**：

| 位置 | 改後 |
|---|---|
| 一次搜尋 `search_run.dart` | `_Phase`：沒在搜、讀回還沒合併、存紀錄中、照條件搜、重試、接著搜、暫停時停下。`isSearching`、`isRestoring` 由它算；存完紀錄才開始、只記照條件搜選的書源、不是重試才算書源總數，都看是哪一段 |
| 放到背景的那一件 `background_search.dart` | `_resuming` 與 `_remaining` 收成一個「下一次接著搜什麼」（沒有就不是接著搜） |
| 搜尋頁 `search_provider.dart` | `_holdingResults` 與 `_attached` 收成 `_Attachment`：沒有、接回等進場、看著；頁面拼的五個組合換成 `SearchStage`，進度那一列、頁首「結束」、進度條直接讀它 |
| 換源 | 不換結構（理由見上） |

`_attached` 沒有改成從 `_background` 與 `_holdingResults` 推出來：離開背景那件時兩個都先清掉才放掉它，推出來的值會漏掉「這一頁不看了」，背景那件永遠收不掉。

讀者看得到、照階段表定的差別：按「重試失敗」後，讀好重試得了的書源、引擎還沒開始（等繁簡字典）的這段，改前頁面先是沒在搜（結果工具列、頁首「搜尋」）再換成搜尋中；現在當下就是搜尋中，同送出搜尋（#30）與接著搜「引擎開始前就算搜尋中，不閃出工具列」。字典已經載好時兩次通知落在同一幀，看不出差別。

改測試的五處都是把讀旗標的地方換成讀 `SearchStage`（`isBackgroundPaused` → 已暫停、`showsMoveToBackground` → 搜尋中），意思沒變。

### 骨架呼吸

`lib/shared/widgets/skeleton/skeleton.dart`：每個 `Skeleton` 的呼吸（`_BreathClock`）、閱讀器的紙與頁首頁尾共用的一口呼吸（`SharedSkeletonBreath`，ADR 0037）、開 App 進場換場前收住一群骨架（`SkeletonRest`，ADR 0031、0035）。形狀（`skeleton_shapes.dart`）只讀呼吸的深淺，不記階段。

**改前**（2026-11-20，`beta` `2a5d2a75`）：

| 欄位 | 意思 | 誰設 |
|---|---|---|
| `_hold`（`ValueListenable?`） | 開 App 的骨架還沒到呼吸的時候：整片最深、計時器不走 | 建在進場底下時掛上，進場的 `breathing` 變 true 時放掉 |
| `_waiting` | 共用的呼吸還沒開始：整片最深、計時器不走 | 共用呼吸一建立、沒人用時（`reset`）設；`begin` 收 |
| `_restFrom`（`double?`） | 收住從哪一個相位開始；不是 null 就是在收住 | `rest`、`restNow` 設；`resume`、`begin`、`reset` 收 |
| `_still` | 收住完了，整片最深、計時器停 | 收住呼完、被藏起來或減少動態時直接算停好；`resume`、`begin`、`reset` 收 |
| `_restarted` | 這口呼吸是從整片最深起的，右邊還沒輪到的位置停在最深 | 開 App 到了呼吸的時候、`resume`、`begin` 設；減少動態、`reset` 收 |
| `_allowed` | 計時器可以走：一般的骨架是沒要求減少動態；共用呼吸是有人在用 | 骨架照 `MediaQuery.disableAnimations`；共用呼吸照 `acquire`、`reset` |
| `_visible`、`_usingShared` | 畫面上看得到（`TickerMode`）；這個骨架算不算共用呼吸的使用者 | 骨架建畫面時 |
| `SkeletonRest._resting` | 一群骨架從 `settle` 到 `release` 之間：這段才出現的骨架一出現就停在最深 | 進場換場前收住、換場播完放開 |
| `_SkeletonState._breathing` | 沒要求減少動態，形狀照呼吸畫 | 骨架建畫面時 |

「現在在哪」散在五個欄位：深淺先看 `_hold != null || _waiting`（最深），再看 `_restFrom` 與 `_still`（收住了或這個位置呼完了就最深），再看 `_restarted`（還沒輪到就最深）；`_start`、`gradient`、`isBreathing`、共用呼吸的 `begin` 各自再拼一次。`_still` 只在 `_restFrom` 不是 null 時才有意思，`_hold` 成立時其他幾個照樣在變、只是被蓋住；共用呼吸在開始前收住，`_waiting` 與 `_still` 會同時是 true。跟著共用呼吸的骨架每一幀照抄來源的六個欄位。

**歷史上因此出錯的**（`git log -G'bool _still' / '_restFrom' / 'bool _waiting' / 'bool _usingShared'` 找到加欄位的 #112、#124、#284、#304，打開 diff 看）：

- #126 審查：收住的計時器比呼吸第一格早一點時，右邊還沒輪到的位置整段沒呼吸。原因是收住多久只看 `_restFrom`，沒看這口是不是從最深起的（`_restarted`）；補進 `_stopAfter`。
- #284 審查：共用呼吸和開 App 進場疊用時，收住與接著呼吸看的是自己沒在走的計時器、相位也對不上（`_shared` 與 `_hold` 同時成立）。改成不准疊用（`Skeleton` 的 assert）。
- #284 審查：被局部 `TickerMode` 藏起來的骨架仍佔著共用呼吸。原因是登記使用只看 `_allowed`，沒看 `_visible`；加了 `_usingShared`。

查過不算：#304 審查「呼吸中又跳章，新骨架邊長出邊沿用舊呼吸」修在紙那邊（舊骨架淡掉時就收住共用的呼吸），`begin` 等收住呼完再起是新加的；#203 的 NaN 是畫的時候位置算不出來，和階段無關。

**階段表**（讀者看到的，照 ADR 0024、0025、0031、0035、0037 與 `docs/design/loading.md`；一個 `Skeleton` 的呼吸，共用呼吸是同一張表）：

| 階段 | 讀者看到什麼 | 可以走到 | 現在一樣嗎 |
|---|---|---|---|
| 等開始 | 整片停在最深、不動：開 App 骨架長出與長完停的那一下；閱讀器的紙長完骨架、正文還沒排好的那 0.5 秒 | 呼吸（開 App 到了呼吸的時候、閱讀器 `begin`，從最深起）；收住了（還沒開始就收住） | 一樣 |
| 呼吸 | 每個位置由深變淺再變深，一輪 1.6 秒（開 App 進場中 0.6 秒），由左而右；從最深起的那口，右邊還沒輪到的位置停在最深；一般的骨架一出現就呼吸，右邊一開始就在淺處 | 收住中；收住了（收住時被藏起來、減少動態或計時器沒在走，直接算停好） | 一樣 |
| 收住中 | 每個位置把這一口呼完、停在最深，停了就不再動；最多再一輪，從最深剛起步時最多一輪半 | 收住了；呼吸（收住途中接著呼吸，照原本的起法繼續）；等開始（閱讀器沒人用） | 不一樣：開 App 的骨架收住途中接著呼吸時，進場的節奏換回一般節奏的那一格深淺跳一下（一格最多變 64/255） |
| 收住了 | 整片最深、計時器停 | 呼吸（接著呼吸、閱讀器 `begin`，從最深起，不跳）；等開始（閱讀器沒人用；開 App 還沒到呼吸的時候就接著呼吸） | 一樣 |

「收住中」那一格的跳動現在的程式碰不到：只有書架的骨架切換接開 App 的進場，進場的 `release` 只在換場播完（這時早已收住）或書架一開始就是內容時呼叫，後者在書架的骨架切換建立時、還沒開始收住。照表改成接著呼吸不跳，免得以後多一個呼叫的地方就踩到。

**不收進階段的**（會和階段同時成立）：

- `_allowed`：一般的骨架是減少動態的設定，共用呼吸是有沒有人在用；任何階段都可能，只決定計時器走不走。共用呼吸沒人用時一律回到等開始。
- `_visible`、`_usingShared`：看不看得到、有沒有登記成共用呼吸的使用者，任何階段都可能；藏起來時收住中直接算停好。
- `_hold`：等開 App 到呼吸的時候那個通知的掛勾，掛著時階段是等開始（或還沒開始就收住了）；是聽通知的資源，不是階段。
- 收住完成的 `Completer`：誰要求收住誰等。跟著共用呼吸的骨架照抄來源的階段，不能連等待一起抄，所以留在各自的呼吸上。
- `_cycle`：一輪多長（開 App 進場中 0.6 秒，之後 1.6 秒），是節奏不是階段。
- `SkeletonRest._resting`：一群骨架的收住窗口，只有一個布林值、沒有和別的旗標互相牽動。
- `SharedSkeletonBreath` 的 `_users`、`_requests`、`_disposed`：使用者數、作廢等著收住後再開始的那一次的號碼、放掉了沒。
- `_SkeletonState._breathing`：減少動態的設定。

**同資料夾不在這一節的**：一般換場 `skeleton_switcher.dart` 的 `_resting`、`_snapshotting`、`_reveal` 是它在開 App 進場裡等到哪一步，和進場一起收（見「進場」）；兩種換場的 `_sweep` 是這一次換場的方向，`CoverReveal._waiting` 只會從等封面變成不等，`_CoverRevealSlotState` 的 `_granted` 配 `_queuedOn` 是排隊建書卡的三個樣子（沒排、排著、放行），都只有一個布林值，不換結構。

**重構時查到並修掉的**：

- 開 App 的骨架收住途中接著呼吸時，一輪的長度從進場的 0.6 秒換回 1.6 秒，計時器照樣在走、整段時間用新的長度重算，那一格深淺最多跳 64/255。改成換長度時從當下的輪數接著算。現在的程式碰不到（理由見階段表下方），先寫會失敗的測試再修。

**改後**：

| 改前 | 改後 |
|---|---|
| `_hold != null`、`_waiting` | `_Waiting`（等開始）；`_hold` 只剩聽通知的掛勾，到了呼吸的時候、階段還是等開始才從最深起 |
| `_restFrom == null && !_still`，配 `_restarted` | `_Breathing`：從哪一輪起算（`shift`）、是不是從最深起（`fromDeepest`） |
| `_restFrom != null && !_still` | `_Resting`：原本那口怎麼起的（一個 `_Breathing`）與從哪個相位開始收；接著呼吸就換回那個 `_Breathing` |
| `_still`（配 `_restFrom != null`） | `_Still` |
| 跟著共用呼吸的骨架抄六個欄位 | 抄計時的輪數與 `_stage` 兩個 |
| 漸層快取比 `_shift`、`_restFrom`、`_restarted` | 比 `_stage` 是不是同一個（每個階段建好就不改） |
| `_start`、`gradient`、`isBreathing` 各自拼 `_hold`、`_waiting`、`_still` | 都看「正在呼吸或收住中」（`_moving`） |

`_allowed`、`_visible`、`_usingShared`、`SkeletonRest._resting` 與共用呼吸的計數照舊（理由見上）。拿掉 `_restarted`、`_restFrom`、`_still`、`_waiting` 與三個快取欄位；對外的 `SharedSkeletonBreath`、`SkeletonRest`、`SkeletonPhase` 與 `Skeleton` 不變，閱讀器的紙照舊。

讀者看不到、碰不到的兩處跟著階段表定：開 App 的骨架在收住途中才掛上進場時，原本計時器被停住、收住永遠等不完，現在照樣收完；還沒到呼吸的時候、已經收住了，到了呼吸的時候原本會多通知一次重畫（深淺不變），現在不通知。
