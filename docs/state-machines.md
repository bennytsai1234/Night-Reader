### 背景工作的生命週期

ADR 0058 的四件背景工作與 ADR 0070 放到背景的搜尋，加上頁面那層。

**改前**（2026-11-19，`beta` `a68a1cc9`）：

| 位置 | 旗標 |
|---|---|
| AI 找書 `lib/core/ai_find/ai_find_session.dart` | `_started`、`_stopped`、`_pausing`、`_paused`、`_disposed` |
| 單一書源 AI 修復 `lib/core/ai_repair/ai_repair_session.dart` | `_running`、`_stopped`、`_paused`、`_disposed`、`_committing` |

| 頁面那層 `lib/features/source_manager/ai_repair/repair_runs.dart` | `_started`、`_finished`、`_seen`、`_paused`、`_resuming`、`_ending` |

「正在暫停」有四種寫法：AI 找書是 `_pausing && !_paused`，兩種修復是 `_paused && _running`，校驗是 `_pausing && !_ending`，搜尋是 `_Settling.pausing`；通知與頁面上的「正在暫停…」「正在結束…」各自照自己的旗標拼出來。

**階段表**（讀者看到的，照 ADR 0058、0070 與 `docs/design/components.md`「狀態用詞」、`screens.md` 各頁定；五件共用）：

| 階段 | 讀者看到什麼 | 可以走到 | 現在一樣嗎 |
|---|---|---|---|
| 未開始 | 頁面剛推入，推入動畫還沒播完；沒有通知 | 做著 | 一樣 |
| 做著 | 通知：標題、做到哪、「暫停」「結束」；頁面：「暫停｜結束」（校驗在書源管理的狀態列，搜尋在進度那一列） | 正在暫停、正在結束、做完 | 一樣 |
| 正在暫停 | 通知內文「正在暫停…」、按鈕拿掉；頁面「正在暫停…」灰掉，「結束」還能按 | 已暫停、正在結束（結束蓋過暫停）、做完（停不下來的那一步做完就是做完，例如正在存修好的書源） | 不一樣：修書源在這時按結束，紀錄與停在半途的 AI 修復不對（下面兩件 bug） |
| 正在結束 | 通知內文「正在結束…」、按鈕拿掉；頁面「正在結束…」灰掉 | 做完 | 一樣 |
| 已暫停 | 通知收掉、位置空出來；頁面「已暫停」與「繼續｜結束」，別件在跑時「繼續」灰掉；被系統收掉、從最近使用滑掉，下次開 App 也是這裡 | 讀回中、正在結束、做完（修書源與校驗開始新的一件時） | 一樣 |
| 讀回中 | 頁面照舊是已暫停，「繼續」灰掉 | 做著、已暫停（接不下去，例如書源不在了）、正在結束 | 一樣 |
| 做完 | 通知收掉；頁面是結果與「完成」 | 看過結果、頁面都關了才放掉（入口改成開新的一件） | 一樣 |

剪貼簿的 AI 修復另有「等貼回」：不是背景工作、沒有通知，只在修復頁上。

**暫停的回饋要不要一致**：一致，五件都照上表。ADR 0058 定的通知（按了內文變「正在暫停…」「正在結束…」、按鈕拿掉）與 `components.md`「狀態用詞」（按了還沒停好時寫「正在暫停…」「正在結束…」，不能再按、灰掉）本來就是五件共用的規則；讀程式與偵測測試確認五件的頁面與通知已經照做，「只有 AI 找書有正在暫停」是內部旗標的差別，讀者看不到。正在暫停時還能按結束、結束蓋過暫停，照放到背景的搜尋已有的規則，五件一起。

**誰記哪個階段**：工作本身（找書、單一修復、整批、校驗、搜尋）記它自己做著、正在暫停、正在結束、已暫停、做完，因為停不停得下來只有它知道（存修好的書源時停不下來）；頁面那層只記工作不知道的：未開始、讀回中、暫停中按了結束、和工作回來之後是已暫停還是做完。頁面與通知讀頁面那層算出的一個階段，不各自拼旗標。

**不收進階段的**（會和階段同時成立）：

- `_disposed`、`_isDisposed`：物件放掉了，任何階段都可能。
- `_committing`：正在存修好的書源，和做著、正在暫停、正在結束同時成立；是「這一段停不下來」的名字，不是階段。
- `_editing`：做完之後在結果頁刪書源中，只在做完時成立。
- `_seen`、開著的頁數：有沒有人看過結果，和做完同時成立。
- 放到背景的搜尋的 `_abandoned`、`_headerWritten` 與 `search_run.dart` 的旗標：屬於搜尋那個候選，這次不動。

**歷史上因此出錯的**：

- #398：按了停止到結果寫完之間重讀清單，剛做完的校驗結果被當成過期丟掉；原因是看「正在校驗」（`_isChecking`），該看「這一輪還沒做完」（`_runInProgress`）。
- #390 審查：繼續讀回期間按結束，晚到的新工作照樣換上去。
- #390 審查：開 App 讀回時只在等待前檢查，等待後沒再檢查。
- #390 審查：暫停中的修復頁，別件做完「繼續」還是灰的。
- #353：頁面返回時直接釋放還在跑的工作，改成先停止、等結束再關。

查過不算：#358 停止閃退是結束 isolate 的方式（`Isolate.immediate`），和旗標無關。

**重構時查到並修掉的**：

- 單一書源 AI 修復正在存修好的書源時先按暫停再按結束：紀錄先寫「已結束，書源沒有改」、再寫「修好了」。原因是結束看 `_paused` 走「已經暫停好」的捷徑，沒看 `_running`。
- 修復異常書源暫停後（或正在暫停時）按結束：整批收尾了，停在半途的那件 AI 修復仍是「已暫停」，點進去「結束」還能按；正在暫停時整批還在跑就先標成做完。原因同上，捷徑也沒有結束那幾件修復。
- 放到背景的搜尋按了暫停、還在等結果檔寫完時按結束：照開始等之前的判斷停成已暫停，沒寫上結束的那一行，之後還能繼續。原因是等寫檔前就決定了要暫停，等完沒再看一次。
- 校驗正在暫停時，書源管理的狀態列落回上次的摘要、「結束」灰掉，直到暫停好。原因是狀態列只看校驗服務「校驗中」，校驗服務在按暫停那一刻就不算校驗中了，這次校驗卻還沒停好。
- 校驗流程本身出錯（讀書源出錯、記錄這個錯時又讀不到）後，校驗服務一直停在「校驗中」，之後的校驗與登入後的自動校驗都直接回傳舊摘要。原因是例外跳過了收尾。

換結構時自己弄出、合併前修掉的（Codex 審查找到）：按了結束、工作本身做完、頁面那層還在刪存檔時，通知換回「暫停」「結束」；校驗流程出錯時，按了停止的那種也會卡在「停下中」（改前按了停止反而能開始下一輪）。

**改後**：

| 位置 | 改後 |
|---|---|
| 共用 `lib/core/background_work/work_phase.dart` | `WorkPhase`：還沒開始、做著、正在暫停、正在結束、已暫停、讀回中、等貼回、做完 |
| AI 找書、單一書源 AI 修復、修復異常書源 | 各一個 `WorkPhase`，只用到自己有的幾個；做著的那一步看「正在暫停或結束」收手；一段跑完照結果與按了什麼定下一個 |
| 頁面那層 | `_RunStage`：未開始、工作在跑、已暫停、讀回中、暫停中按了結束、做完；`run()` 直接回傳暫停好了還是做完；對外的 `phase` 在工作跑的時候照工作本身；通知的「正在暫停…」「正在結束…」在這裡統一換 |
| 放到背景的搜尋 | `_Settling` 換成 `WorkPhase`（做著、正在暫停、正在結束） |
| 從書源管理按的校驗 | `WorkPhase`：做著、正在暫停、正在結束，跑完記成已暫停或做完 |
| 校驗服務 | `_CheckPhase`：閒著、校驗中、停下中；開始新的一輪要閒著 |

頁面的按鈕列、狀態列與通知只讀階段。工作本身已經停好、頁面那層還在收尾時，頁面讀到它要去的那一頭（正在暫停或正在結束），通知不再更新、等收掉。讀者看得到的差別，都是照階段表把五件拉齊：

- AI 找書正在暫停時按結束：原本「暫停」那列還寫「正在暫停…」、下面又寫「正在結束…」，現在照其他四件，「暫停」灰掉、「結束」寫「正在結束…」。
- 已暫停的搜尋按結束、還在寫結束的那一行時：進度那一列原本仍寫「已暫停」，現在寫「正在結束…」。
- 上面三件修掉的 bug。

改測試的兩處（讀者看不到的舊意思）：沒開始就結束的一批，通知原本寫「正在結束…」；做完的一批原本仍算「按了結束」。現在「正在結束」只在還沒停好時成立。

### 書源管理

書源管理頁的清單（`lib/features/source_manager/source_manager_provider.dart`）：誰正在讀、改書源，其他改書源的動作要不要等。

**改前**（2026-11-20，`beta` `660b61a1`）：

| 旗標 | 意思 | 誰設、誰收 |
|---|---|---|
| `_isLoading` | 清單在讀（一建立就是，等進場動畫播完才讀） | 讀清單（`loadSources` 預設會設）與匯入都設 |
| `_loadOwnsLoading` | `_isLoading` 是讀清單設的，不是匯入設的 | 最新一次讀清單收尾時，是自己設的才收 `_isLoading` |
| `_isBatchOperationInProgress` | 批次作業中（刪、移動、改分組、校驗、清標記） | 批次作業開頭設、結束收；裡面的重讀照樣再設 `_isLoading` |
| `_mergingDuplicates` | 讀清單時正在併重複書源（ADR 0062） | 讀清單裡設、併完收 |
| `_syncReloadPending` | 同步套用了別台的書源，重讀已經排著、等頁面露出來 | 收到同步通知時設、開始重讀前收 |

一起決定的四個問題，各自用不同的組合拼：

- 整份清單忙不忙（`isMutationBusy`，選單、多選工具列、分組管理灰掉）：`_isLoading` 或批次、校驗中、併重複書源、有一列在改。
- 這一列能不能按（`isSourceLocked`）：批次、校驗中、這一列在改；不看載入與併重複書源。
- 能不能開始改一列（`_beginSourceMutation`）：不在載入、不在批次、不在校驗；不看併重複書源。
- 能不能併重複書源：不在批次、不在校驗、沒在併、沒有一列在改；不看載入。

同時成立的有：批次作業裡的重讀（批次與載入都是真）、第一次讀清單時併重複書源（載入與併都是真）、匯入裡的重讀（`_isLoading` 是匯入的、重讀不收）。`_loadOwnsLoading` 就是為了分清楚最後一個。

**歷史上因此出錯的**：

- #33：切一個開關整個清單重建、所有開關變淡。清單用不用可拖曳的版面看 `isMutationBusy`，它把「有一列在改」也算進去；改成版面只看排序與篩選，單列修改只鎖那一列。
- #33：置頂、置底走單列修改，和別列的修改同時改寫全部書源的順序；改成批次作業獨占。
- #56：顯示載入中的讀取被背景的重讀（校驗做完）蓋過時，`_isLoading` 一直不收，清單永遠在載入。原本只有顯示載入中的那次讀取收得掉，被蓋過的又因為不是最新一次而不收；改成最新一次收尾就收，同時加 `_loadOwnsLoading`，免得收掉匯入設的。

查過不算：`_isLoading` 一建立就是真（#69）、`_syncReloadPending`（#235）、`_mergingDuplicates`（#380）都是新功能帶進來的，不是修旗標組合。

**階段表**（讀者看到的，照 ADR 0018、0024、0062 與 `docs/design/screens.md` 的書源管理；整份清單現在被誰占著）：

| 階段 | 讀者看到什麼 | 可以走到 | 現在一樣嗎 |
|---|---|---|---|
| 第一次讀 | 進場動畫播完才讀；骨架的列數與字照上次，搜尋框、多選工具列照上次有沒有書源留位置；選單灰掉 | 閒著（讀到清單，或讀不到時是錯誤頁與「重試」） | 一樣 |
| 閒著 | 都能按；切開關、刪一個書源時只鎖那一列，別列照樣能改 | 重讀、匯入、批次作業 | 一樣 |
| 重讀 | 改了書源之後、從編輯頁回來、按了「重試」時：清單留著（空的時候畫骨架，例如按了重試）；選單、多選工具列灰掉；列看起來能按，切開關不理 | 閒著 | 一樣（列看起來能按卻不理：維持，見下） |
| 匯入 | 寫進資料庫（含匯入自己併重複書源）：同重讀；頁面的匯入流程另有進度條、列灰掉 | 重讀（寫完）、閒著（寫入出錯） | 不一樣：不在閒著時按了匯入，提示「未匯入有效書源」，其實是書源管理正忙 |
| 批次作業 | 刪、移動、改分組、校驗、清標記：選單、工具列、每一列都灰掉，不能拖 | 閒著 | 一樣 |

**併重複書源**是有名字的動作，不是階段：它在讀清單裡做，會和第一次讀、重讀、閒著（背景重讀時）同時成立。併的時候：

| 誰 | 現在 | 照 ADR 0062 該怎樣 |
|---|---|---|
| 批次作業、匯入 | 不理 | 同現在 |
| 改一列（切開關、刪） | 照做：切了要留下的那個的開關，合併存回它時可能蓋掉；刪掉要留下的那個時，那組不併（合併在交易裡重查），或書剛搬過去它就被刪 | 不理，同重讀時 |
| 另一次讀清單 | 不併、直接讀：讀到併之前的清單，併完的那次又因為不是最新一次而丟掉結果，清單留著已經刪掉的重複書源；讀的途中合併跑完、讀到的是併之前的也一樣 | 等它併完再讀，讀完照常判斷要不要併 |
| 畫面 | 背景重讀時開始併不重畫，看起來是閒著 | 同現在 |

**誰收**：第一次讀與重讀由最新一次讀清單收尾時收；匯入與批次作業做完自己收，這時最新一次讀清單還沒讀完（背景重讀蓋過了自己的重讀）就換成重讀、交給它收。匯入寫完就換成重讀；批次作業裡的重讀不碰階段，原本的 `_loadOwnsLoading` 因此不用了。背景重讀（校驗做完、修書源做完、同步套用）不是階段：不鎖任何東西，誰是最新一次照讀取的序號定。

**不收進階段的**（會和階段同時成立）：

- 正在改的那幾列（`_pendingSourceMutations`）：一次可以好幾列，和閒著、重讀同時成立（刪一個書源之後的重讀）。
- `_syncReloadPending`：同步的重讀排著、等頁面露出來，任何階段都可能；它只把連續的通知併成一次。
- `_disposed`、`_listeningSync`：物件放掉了、有沒有在聽同步。
- 校驗中（`checkService.isChecking`）：校驗服務的，背景工作也會校驗。
- 頁面的 `_isImporting`：整段匯入流程（選檔、抓網址、預覽面板開著）；預覽面板開著時書源管理其實閒著，背景重讀照常，不是同一段。

**維持現狀、等使用者看圖選的**：重讀與併重複書源時列看起來能按、按了不理。讓列也灰掉會在每次刪一個書源、從編輯頁回來時整份清單閃一下（#33 修過切開關時所有開關變淡）。

**查到並修掉的**：

- 併重複書源時開始的背景重讀（校驗做完、修書源做完、同步套用）不等合併、直接讀：放出併之前的清單、收掉第一次讀的骨架，併完的那一次又因為不是最新一次而丟掉結果，清單留著已經刪掉的重複書源。原因是有合併在跑時就跳過、照讀；改成等它併完再讀。
- 併重複書源時切開關、刪一個書源照做：切了要留下的那個的開關，合併存回它時可能蓋掉；刪掉要留下的那個時那組不併，或書剛搬過去它就被刪。原因是能不能改一列沒看併重複書源。
- 預覽面板開著時書源管理才忙起來（背景工作開始校驗、背景重讀併重複書源），按了匯入提示「未匯入有效書源」；改成「匯入失敗：書源管理正在改書源，等它做完再匯入」。
- Codex 審查找到、改前就有的：等合併的重讀等完只重讀、不併同步新帶進來的重複書源；讀的途中合併跑完，照樣放出併之前的清單；開始併的那次被較新的蓋過時，合併出錯沒有紀錄。改成記下併完過幾次，讀的期間有合併跑過就等它併完重讀，之後照常判斷要不要併；開始併的那次記下錯誤。

換結構時自己弄出、合併前修掉的（Codex 審查找到）：批次作業自己的重讀被背景重讀蓋過時，批次作業一做完就放開清單，選單在還留著已刪書源的清單上能按；匯入寫進去時背景工作在跑、匯入自己沒併，之後的重讀也不併。前者改成交給最新一次讀清單收，後者改成匯入寫完就換成重讀。

**改後**：

| 改前 | 改後 |
|---|---|
| `_isLoading`、`_loadOwnsLoading`、`_isBatchOperationInProgress` | `_ListWork`：第一次讀、閒著、重讀、匯入、批次作業；占著的由自己收 |
| `_mergingDuplicates` | `_merging`：正在跑的那次合併，加上併完過幾次（`_mergesDone`）；讀的期間有合併跑過就等它併完重讀，能不能併只在 `_canMerge` 一處判斷 |
| `_syncReloadPending` | 照舊（理由見上） |

`isLoading`、`isMutationBusy`、`isSourceLocked`、`canReorder` 照舊對外，都從階段與 `_merging` 算；拿掉沒人讀的 `isBatchOperationInProgress`。讀者看不到的差別：批次作業裡的重讀不再算載入中（清單有書源，骨架與「刪光時結束多選」都看不出）。
