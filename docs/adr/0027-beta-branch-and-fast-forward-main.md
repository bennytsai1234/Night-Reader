# 日常改動進 beta、合併就發測試版；main 只快轉到用過的 beta 發正式版

新增長期分支 `beta`，GitHub 的預設分支是 `beta`。功能與維護在從 `beta` 開的分支上做，走 PR 合併進 `beta`（改到 App 內容的 PR 由 Codex 審查、squash 合併、交接跟著 PR，照 ADR 0014）；只改說明文件時直接在 `beta` 上改。

推上 `beta` 時，`android-release.yml` 把上一個發布之後累積的 App 改動自動發成測試版（tag 與「接收測試版更新」照 ADR 0004）。沒有 App 改動（例如只改文件）就不發，照常結束；改了 App 卻沒寫 `CHANGELOG.md` 的「未發布」時這次執行失敗（ADR 0010）。手動以 `channel=beta` 執行只用在補發自動那次沒發出去的測試版。

維護者用過測試版、說要發正式版時：在 `beta` 推一個只改版號的提交（`release: bump version to X.Y.Z`，同時把「未發布」改成 `## X.Y.Z`），再把 `main` 快轉到這個提交、推上去，`main` 收到就發正式版（ADR 0002）。`main` 不收其他任何提交：CI 在 `main` 收到不在 `beta` 上的提交時直接失敗。網站照舊從 `main` 部署，內容跟著正式版走。`beta` 與 `main` 的分支保護都只禁止強制推送與刪除。

為什麼這樣定：2026-10-19 使用者定的，日常維護與新功能都先進 `beta`，自己用過沒問題再上 `main` 發正式版，跟公司專案的 `dev`／`master` 一樣。合併就發測試版，是因為每次合併總要有人裝起來用。ADR 0004 曾考慮過長期 `beta` 分支，因為要同步兩條受保護的分支、容易衝突而沒採用；這裡 `main` 從不自己提交、只快轉，沒有要同步的東西。ADR 0014 把測試版從自動改成手動，是因為當時每推一次 `main` 就發一版，會收到內容差不多的更新；現在一次合併是一個 PR，常是好幾條分支併成一批，只改文件也不發，次數比當時少。

升版號的提交放在 `beta`、`main` 只快轉，是被 versionCode 逼出來的：versionCode 取發版那個提交的提交數（ADR 0004），測試版從 `beta` 發、正式版從 `main` 發，兩邊必須是同一條歷史，數字才會只增不減，裝了測試版的人才升得到正式版。

## 考慮過的做法

- **升版號的提交推到 `main`，再把 `main` 併回 `beta`**：兩條分支各有自己的提交，要來回同步，正是 ADR 0004 擔心的衝突；同步之前兩邊的提交數也是岔開的。
- **用 merge commit 或 PR 把 `beta` 併進 `main`**：`main` 會多出自己的合併提交，同樣讓兩邊的提交數岔開。
- **測試版維持手動發（ADR 0014）**：使用者要的是合併完就有測試版可以裝來用，不必再另外喊一次。
- **維持只有 `main`**：`main` 上隨時混著還沒用過的改動，網站與正式版之間沒有一條「用過沒問題」的界線。
