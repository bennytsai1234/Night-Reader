# 修書源、校驗書源與 AI 找書離開夜讀也繼續、可以暫停，通知欄顯示進度

修復異常書源一次要十幾分鐘（每個網站等 AI 想 5 到 10 輪），原本修的時候得一直開著那一頁、螢幕不關，返回就停。使用者 2026-11-10 提出要丟到背景、通知欄顯示進度，邊讀書邊修；2026-11-11 談定下面五件。

在夜讀裡換頁、讀書時，這些工作本來就在主 isolate 繼續跑；真正會斷的是離開夜讀（切到別的 App、關螢幕），系統把沒有前景服務的 App 凍結或收掉。所以要做的是「離開也不斷」與「通知欄的進度」。

2026-11-15 使用者回報：AI 找書跑的時候按 Home，從通知點回來 App 從骨架重開，找書不見，舊通知殘留、按了沒反應。舊通知還在，表示程序沒死：Activity 被收掉（或按返回關掉）時，audio_service 在沒播音、沒人連著播放服務時把整份 Flutter 引擎拆掉（`AudioServicePlugin.onDetachedFromActivity` → 斷線 → `AudioService.onDestroy` → `disposeFlutterEngine`），工作只在記憶體，跟著沒了。同一天談定下面的「暫停與結束」。

## 決定

- **推翻「修的時候不能離開頁面」**（畫面規格「AI 修書源」「修復異常書源」的返回等於停止，與當時否決的「背景跑加膠囊」）。當初的理由是修的時候可能正在編輯或校驗同一個書源；現在存修好的書源前會核對書源有沒有被改過或刪掉，改過就不存（`saveRepairedSource`），整批的重新校驗碰到別的校驗在跑就停下說原因。開始後可以返回，工作照跑。
- **涵蓋四件使用者按了才開始的長工作**：修復異常書源、單一書源的 AI 修復、校驗書源（使用者選的範圍是「修書源與校驗書源」），與 AI 找書（ADR 0060 加的）。背景下載不做：書架的網路書會自動下載（ADR 0008），每加一本就冒一條通知，和「預設克制」相衝，要做另外談。換源搜全部書源通常一分鐘內結束，不列。
- **一次只跑一件**：四件共用一個位置，一件在跑時其他幾件的入口是灰的（照原本「校驗中不能 AI 修復」），通知欄最多一條，不做排隊。整批修復裡的重新校驗算整批的一部分，不另外佔。
- **自己寫一個小的前景服務**（Kotlin，類型 `dataSync`）：只負責讓系統別凍結夜讀、讓 CPU 在關螢幕時照跑（部分喚醒鎖），與通知欄的進度；工作照舊在主 isolate，修書源與校驗的程式不搬家。工作跑的時候前景服務用 `MediaBrowser` 連著播放服務（audio_service 的 `AudioService`），Activity 不在時引擎才不會被拆；工作結束放開。開 App 時收掉上次留下的通知與前景服務（引擎重開過時舊的沒人收）。
- **通知**（使用者在 HTML 候選上選了甲）：不跳出、不出聲，只在通知欄；標題是工作，內文是做到哪一段和數字，和頁面上那一段的副標同字；按鈕是「暫停」「結束」（按了內文變「正在暫停…」「正在結束…」、按鈕拿掉；哪幾顆由 Dart 給），點通知本身回到那一頁。進度條是整件的進度：修復異常書源四段各佔 25%（第幾段的 25% 加這一段做完的比例），校驗只有一段；單一書源的 AI 修復不知道總數，不畫進度條，內文是修復頁正在做的那一步。做完、暫停好就收掉，不留「做完了」。
- **暫停與結束**（使用者 2026-11-15）：兩顆鈕「暫停」「結束」，用詞全 App 一起改（`docs/design/components.md`「狀態用詞」）。按 Home、切到別的 App 照跑；從最近使用滑掉、被系統收掉（含 `dataSync` 的 6 小時到）都算暫停。每做完一步存一次進度（一件一個檔，不同步、不進夜讀的備份），下次開 App 那件工作的頁面顯示已暫停，要不要按「繼續」由使用者決定，快取過不過期也由使用者判斷。接著做到多細：
  - AI 找書：從最後存的那一輪開頭接著問（對話、看過哪些書的詳情與正文、發現頁的編號都存）；暫停時做到一半的那一輪重問，搜過的結果不存，要下一批會重搜。
  - 校驗書源：只校驗剩下的，數字接著數，報告接在前面的結果後面；停下時正在校驗的那幾個重校。
  - 修復異常書源：每有書源定案就存一次；繼續時用同一批書源重開，已經有結果的帶著結果，其他照原本的規則走（24 小時內校驗過的沿用，ADR 0054），暫停時正在 AI 修的書源從頭重修（使用者選）。
  - 單一書源的 AI 修復：從頭重修這個書源。

  按「結束」就收尾，結果留著（找書存成過去的找書），存檔先刪再存結果，不能再接著做。暫停中的不佔一次一件的位置。AI 找書的入口推回暫停的那一次；修書源與校驗開始新的一件時，暫停的那件就結束（使用者選；否決過一直灰著別的入口、跳提示框問、別的入口推回暫停的那一頁），同一個書源、同一批的入口推回暫停的那一頁。
- **回到那一頁**：書源管理的「修復異常書源」「AI 修復」在那件工作還在跑、或做完還沒看過結果時，推的是同一批的頁面，不重開；看過做完的結果、離開頁面後才算結束。書源管理在工作做完時重讀清單。
- 第一次開始這幾件工作時要通知權限（原本只在第一次朗讀時要）；沒給的話工作照跑，只是通知欄看不到。

## 考慮過的做法

- **維持返回等於停止、只開著螢幕**：原本的做法；使用者要邊讀邊修。
- **只做修書源**、**連背景下載一起做**：見上面的範圍。
- **用 `flutter_foreground_task`**：做的和自己寫的一樣，多一個要跟著升級、可能要修補的第三方套件，功能比需要的多。
- **搬到 `workmanager` 的背景工作**：滑掉 App 也不會斷，但書源引擎、資料庫、AI 連線都要在另一個 Dart 引擎重開一份，等於重寫整批修復與校驗。
- **通知的寫法**：乙（標題帶數字、內文跟著 AI 每一輪換）字一直跳；丙（不畫進度條）看不出進度。四段各自從 0 跑到滿的進度條換段時會倒回去，改成每段佔 25%。
- **做完留一條「做完了」的通知**：使用者選收掉。
- **只修引擎被拆、不存進度**：程序被系統殺掉時照樣全沒；存進度兩種原因都有效，所以兩樣都做。
- **被收掉後下次開 App 自動接著做**：使用者要自己決定（快取可能過期、可能不想再花用量）。
- **AI 修書源接到同一輪**（同 AI 找書）：要存修到一半的書源、開場的校驗與試抓，與 AI 用頁碼指的整頁網頁原文，整批同時修好幾個時每輪都要寫；使用者選從這個書源重修。
- **校驗膠囊只放一顆「暫停／繼續」、「結束」放在詳情對話框**：使用者在候選圖上選兩顆都放膠囊上。
- **單一書源修復畫來回跑的動畫條**：一直在動，不夠安靜；不放進通知：離開夜讀就斷。

## 觸點

| 觸點 | 答案 |
|---|---|
| 書源類型、校驗怎麼判斷、付費章節 | 不適用：判斷照舊，只是離開夜讀不斷 |
| AI 修書源 | 做：見上 |
| 要登入、要網頁驗證 | 照 ADR 0038：背景工作碰到就停、記成狀態，整批修復本來就把需要登入、驗證的書源列為不修 |
| 搜尋、發現、換源、匯入 | 不做：換源搜尋一分鐘內結束 |
| 書架、書籍詳情、檢查新章節 | 不適用 |
| 下載、清除已下載 | 不做：見上面的範圍 |
| 閱讀器、播放器、偏好、進度、統計、書籤、朗讀 | 不適用；沒有新設定（ADR 0030） |
| 通知、鎖定畫面 | 做：新的通知頻道「背景工作」，和播放的媒體通知（ADR 0055）分開；鎖定畫面照系統設定 |
| 同步、備份、匯出 | 不適用：暫停的存檔不同步、不進夜讀的備份 |
| `PRIVACY.md` 與「隱私說明」 | 不改：不多送任何資料。App 的「權限」頁「通知與背景任務」一段改寫：通知權限也用在修書源、校驗書源的進度，跑的時候開前景服務 |
| `README.md`、網站、`GLOSSARY.md` | 不做：是修書源與校驗的改進，不是新的一類功能 |
| `docs/design/` | 做：`screens.md` 的 AI 修書源、修復異常書源、書源管理 |
| iPhone | iOS 不讓 App 在背景跑這種工作，沒有通知；離開夜讀後被系統收掉時照暫停處理，下次打開顯示已暫停 |
| 自動巡檢 | 做：新的服務資料夾與 Kotlin 檔排進分段 |
| 小說、漫畫、有聲、本地書 | 三類書源一樣修、一樣校驗；本地書不適用 |

## 後果

- 使用者 2026-11-11 回報播放通知在 vivo 上「多跳一個」，原因還沒查清（`PLAN.md`）；這個通知用新的低重要性頻道、只提醒一次、靜音，前景服務只在開始時啟動一次、之後只更新，是不靠手機能做的防備。在 vivo 上會不會跳，和播放通知是同一個待查的問題。
- 修的時候不再強制開著螢幕：前景服務加喚醒鎖讓關螢幕也照跑。
- 工作跑的時候前景服務連著播放服務，Activity 不在時引擎留著、工作照跑。這段保護靠 audio_service 0.18.19 的行為（`AudioService` 有人連著就不會 `onDestroy`、不拆引擎）與 Flutter 的 `FlutterActivity` 不拆外部給的引擎（`shouldDestroyEngineWithHost`），升級 audio_service 時要再讀一次它的拆引擎流程。
- 暫停的存檔只存每一步做完的樣子：AI 找書每輪寫一次（整段對話，越到後面越大），校驗每個書源寫一次（寫入合併，只寫最後一份）。
