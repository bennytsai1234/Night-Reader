# 正文在排版前修復明確的錯誤換行

網路書源、TXT 與 EPUB 匯入的正文，有時把視覺折行存成真正的換行，例如：

> 「請進。
> 」一個悅耳的女性聲音在門後傳來。

Reader V2 原本每遇到換行就建立新的來源段落，讓第二行的收引號變成下一段開頭。ADR 0026 的「避頭尾」只處理同一來源段落內的視覺換行，不能跨越這個邊界修復。

## 做法

- 在內容轉換 worker 套完書的替換規則、執行 normalizeTypography **之前**，先用 SemanticParagraphFormatter 整理來源換行；對白的彎引號接回中文句子後才能正確轉成「」。
- 一般單一換行仍當作來源段落，不直接把所有句子或段落黏起來。只合併有明確排版證據的邊界：下一行以收尾標點開頭、上一行以開頭標點結尾、成對的「……」「——」被折開；來源出現大量相同字數的固定欄寬硬折行時，合併不以句末標點收尾、也不以新對話開始的相鄰行。
- 固定欄寬只在沒有空白行的連續區間內判斷：至少五行、其中至少四行且至少四分之三的行長落在同一個 14–120 字的欄寬正負一字之內。一般網路小說每段長度不一，不會因此被合併。這是保守規則；沒有可靠結構證據的換行留給來源決定。
- **空白行一律是確定的段落邊界**，不得跨過它修復，包含使用者開啟「重新分段」時。來源插圖的私用區記號仍留在原位；判斷兩行首尾標點時跳過記號，但不丟掉它。
- ReaderV2Content.fromRaw 可以整理直接傳入的原始正文；worker 已整理過的正文以 repairBrokenLines: false 建立，避免在空白行被下游濾掉後再修一次，破壞明確段落邊界。
- 選字用的替換規則原文，在同一個來源處理階段套用相同的段落判斷，讓來源段落與顯示段落保持一一對應。
- 整理後的 displayText 仍是選字、進度、朗讀、標註、插圖與 contentHash 使用的共同文字座標；既有視覺換行、ParagraphTextMap、排版快取與繪製流程不另建立第二套。原始儲存正文不覆寫。

## 不做的事

- 不憑句號就推斷另一個語義段落，因為一句話不等於一段話。原本針對「重新分段」明確選用的長單行強制切句行為仍保留。
- 不跨空白行修補，不把正常的兩行對話合成一段，不修改原文字、猜測遺失的標點或將任意短詩行接成小說句子。
- 不重寫 Flutter 的字形塑形或視覺換行：字寬、英文半格補白、避頭尾與字距的規則仍由既有引擎決定。

## 驗證

以同一份原文與排版設定檢查：收引號錯位、行尾開引號、成對符號、固定欄寬、一般段落、連續對話、空白行、插圖記號，及整理後的章節段落與正文雜湊。實機仍須確認開書、換章、選字、朗讀、插圖和捲動效能沒有回歸。
