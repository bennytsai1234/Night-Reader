# 流暢與動畫完整優先，等待時間其次

改進體驗時，首要目標是整體使用起來流暢、每段動畫完整播完。骨架停得久、內容晚一點出來都可以；不為了讓東西早點出現而縮短或跳過動畫、讓工作疊到動畫上，也不為了省時間加上會犧牲流暢的快取或捷徑。使用者的判斷（2026-10-17）：在意的是使用體驗，等待時間不算在使用體驗裡。

2026-11-16 使用者要加快開 App：等待變短、而流暢與動畫完整都不受影響的改動可以做；兩者衝突時流暢優先。第一件是開 App 的底色不再等朗讀引擎（ADR 0018「開 App 的底色」）。

這條把 ADR 0017（開 App 先看骨架是想要的流程）和 ADR 0018（寧可內容晚一點出現，也不讓動畫掉幀）背後的取捨講成通則：評估一個改動，先問畫面順不順、動畫有沒有完整播完，再看使用者少等了多久。

## Considered Options

- **縮短書架等封面的上限（0.3 秒）與淡入時間（0.4 秒）**：只換來等待短一點，淡入也變得倉促，否決。
- **等待一律不列入考量**（2026-10-17 到 2026-11-16 的寫法）：拿掉一段不護著任何動畫的等待也不做，開 App 的底色因此多等系統朗讀服務約 0.1～0.8 秒。2026-11-16 使用者要加快開 App，改成上面的寫法。

## Consequences

- 縮短等待的改動要量得出動畫沒有變差（手機的系統追蹤或 `test/frame_budget/`）才做；量不到就不做。
- 只為了讓東西早點出現、代價是動畫被打斷或掉幀的改動不做，例如把整個書架存起來直接畫出書（ADR 0024）。
- 之後評估效能或載入相關的改動，先看會不會掉幀、會不會打斷動畫，載入快慢放在後面。
