# 規則 JS 等網路時整條書源 isolate 停住，拿到的就是結果；書源 isolate 開四條

書源規則的 JS 呼叫 `java.ajax`、`java.get`、`cache.get`、`cookie.get`、`source.getVariable` 這類要等網路或資料庫的函式時，所在的書源 isolate 整條停住，等網路 isolate（`SourceIo`）做完再繼續，JS 拿到的就是結果本身，和 Legado 的 Rhino 一樣。不論呼叫寫在最外層、書源自己的函式、`jsLib`、`map` 的回呼還是 `eval` 裡都一樣。

原本的做法是執行前掃一遍程式，在認得的呼叫前面補 `await`，再包成非同步函式執行。寫在書源自己的函式裡的呼叫補不到，源倉庫 803 個文字書源裡有 148 個（18%）這樣寫，拿到的是還沒完成的結果。使用者 2026-10-26 在「做成同步等待」與「把補 `await` 做得更聰明」之間選了前者。

## 怎麼做

- **書源 isolate 從一條改成四條**（`SourceIsolate.workerCount`）。停住期間那一條上的其他書源工作都在等，一條的話一個書源在等網路，其他書源全部排隊。同一個書源的工作送到同一條（共用 jsLib 與引擎快取）；下載一輪用書的網址，那一輪的書與章節只存在規劃它的那一條。每條約多 8MB，幾乎都是繁簡字典。
- **網路 isolate** 替停住的書源 isolate 發請求、讀資料庫與檔案、問平台資料夾在哪。它自己從不停住、不跑規則 JS；網址裡的 JS 在書源 isolate 組網址時就跑完了。停住的書源 isolate 在一個由主 isolate 擁有的信箱（`native_synchronization` 的 `Mailbox`）上等，結果由主 isolate 放進去；書源 isolate 被結束時關掉信箱，停在原生等待裡的它才結束得了。
- **不會互相等死**：停住的那條手上若拿著別人要的東西，兩邊就永遠等下去。找到兩種，各有一則先拿掉修正、確認會逾時的測試：
  1. 限流名額：同一個書源只准一個請求時，停住的那條手上凍著的請求佔著名額。停住時它的名額先交回。
  2. drift 交易：drift isolate 有交易進行時其他查詢都要排隊，停住的那條手上若有一段交易做到一半，替它讀資料庫就排在交易後面。網路 isolate 另開一條直接連到資料庫檔案的連線（`AppDatabase.separateConnection`），資料庫改用 WAL，讀和寫可以同時進行。
- 主 isolate 不能停住（畫面會卡死，主 isolate 也是 Cookie 檔與限流的擁有者）。書源 isolate 開不起來、書源工作改在主 isolate 執行時，規則 JS 要等的呼叫直接失敗。

## 和 ADR 0028 的關係

0028 定的是「一條常駐的書源 isolate」，並否決過「閱讀與下載另開一個書源 isolate」，理由是多一份 JS 引擎與記憶體、而且網路等待時照常輪流。改成同步等待後網路等待不再輪流，所以改成四條。0028 其他的部分（Cookie 檔與限流在主 isolate、資料庫共用 drift isolate、送過去的書與章節是複本）照舊。

## 考慮過的做法

- **把補 `await` 做得更聰明**（找出呼叫網路的函式改成非同步、在呼叫處補 `await`）：回呼裡補了反而改變行為（`map` 變成一串還沒完成的結果、`forEach` 不等每一筆、`sort` 的回呼不能是非同步），物件方法與傳來傳去的函式要真的看懂語法才判斷得出來，改錯會把能用的書源改出語法錯誤，也永遠補不完。
- **JS 搬到另一條專門的 isolate，每次呼叫 Dart 都跨過去**：書源 isolate 不必停住，也不會互相等死；但 2026-10-26 實測一次跨 isolate 的來回約 78 微秒（桌機），Jsoup 元素這類一章要呼叫上千次的規則會多出一兩秒，解析流程也要全部改成等 JS。
- **停住的書源 isolate 自己開同步的 SQLite 連線讀**：網路請求要讀資料庫裡的 Cookie，還是得處理網路 isolate 碰資料庫的情況。
- **維持一條書源 isolate**：搜尋一次上百個書源時，每個要等網路的規則 JS 都讓其他書源排隊。

## Consequences

- 補 `await` 的改寫器、非同步包裝與 Promise 橋整個拿掉；解析流程裡為了等 JS 寫成的非同步分支（`getStringAsync` 這一類）也一起拿掉，規則一律同步執行。
- 規則 JS 停住時中途停不下來：書源工作被取消時，主 isolate 替它把交出去的請求一起取消，它醒來後同一個工作再發的也直接以取消結束（它這時還沒收到取消的通知）；網路請求本身有 15 秒的逾時。
- 規則執行到一半出錯不再整段重跑：原本為少數被 QuickJS 誤判語法的舊規則寫的後備做法不分錯誤種類，請求與 `java.put` 這類動作會做兩次，被取消的請求也會再發一次；現在只在語法錯誤時才用。
- 網路 isolate 那條連線的寫入（例如刪掉過期的快取）不會更新別人的 `watch()`；它只替停住的書源 isolate 讀，寫入不等它寫完。
- `java.queryTTF` 的網址字型原本傳回還沒完成的結果，現在也拿得到。
