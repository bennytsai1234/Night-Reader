# 測試版說明取 PR 標題、合併一批發一版；CI 只在 PR 與 beta 上跑

**測試版說明**：測試版的說明是上一個發布之後，`beta` 上每個改到 App 內容的提交標題。squash 合併的提交標題就是 PR 標題。`tool/changelog.sh titles` 會去掉 `fix(reader): ` 這類前綴和結尾的 `(#123)`，一個 PR 一行。所以 PR 標題要寫成讀者看得懂的一句，不寫書源名稱與網址，145 字以內。開 PR、改標題或推新提交時，`pr-title.yml` 會檢查改到 App 內容的 PR 的標題。每個 PR 不再寫 `CHANGELOG.md`，`## 未發布` 這一段拿掉了。`CHANGELOG.md` 只放正式版的說明：使用者說要發正式版時，從 `titles <上一個正式版> HEAD` 與各測試版的說明整理成一兩句介紹加最多八條，寫成 `## X.Y.Z`，跟版號提交一起推。

**一批發一版**：推上 `beta` 不再自動發測試版。合併的人（ADR 0047）合完一批，等 `beta` 的 CI 通過，再執行一次 `gh workflow run android-release.yml --ref beta -f channel=beta`，這一批就發成一個測試版。CI 沒通過就先修好再發。沒有 App 改動時這次執行照常結束、不發。正式版照舊由 `main` 快轉觸發。

**CI 的時機**：CI 在開 PR、PR 有新推送、推上 `beta` 時跑；只改說明文件的推送不跑。PR 上跑的是分支併進目前 `beta` 的樣子，比只測分支本身更接近合併後的結果。做的途中推分支只是備份，不跑 CI。

為什麼這樣定：2026-11-07 使用者定的，和 ADR 0047 一起。

- **更新說明**：每個 PR 都要把一條擠進已經滿八條的「未發布」，還得改寫別人寫的條目。沒寫或寫太長，CI 與發版就失敗：2026-10-31 到 11-07 這一週約 20 次，佔了 54 次發版裡 10 次失敗的大半。使用者說「為了這個多走好幾步不值得」，測試版的說明「模糊一點沒有關係」。ADR 0010 當初不用 commit 標題，是因為一件事拆成好幾個 commit、有英文前綴；現在一個 PR squash 成一個提交，前綴也由工具去掉，那兩個理由已經不在。
- **發版次數**：每合一次就發一版，11-02 一天發了 15 版，手機一直跳更新。GitHub 的機器不收錢（公開 repo），干擾的是使用者。
- **CI**：同一週約 200 次 CI，三分之二是做到一半推分支時跑的，失敗的 28 次多半沒有意義，GitHub 還會寄失敗通知。

## 考慮過的做法

- **照舊每個 PR 寫一條「未發布」，只是寫短一點**：並行合併時還是會在這個檔案衝突，也還是會擠滿八條。
- **推上 `beta` 照舊自動發，拿掉排隊設定讓連續合併併成一版**：GitHub 的排隊只會取消還在等的那次、不取消正在跑的那次，連續合併三次還是會發兩版；讓新的取消正在跑的，又會取消掉同一組裡正在發的正式版。
- **推上 `beta` 自動發，但先等幾分鐘，`beta` 有更新就讓給下一次**：要猜合併之間會隔多久，每版也平白晚幾分鐘。
- **只有使用者說「發測試版」才發**：合併完要多說一句，使用者要的是合完就能裝來用（ADR 0027）。
- **途中推分支照舊跑 CI**：沒有人要等它，結果大多沒有意義。
- **途中不推、收尾才推**：做到一半的東西沒有備份，也違反全域指示「每段驗證過就 commit 並推上」。
- **PR 標題的檢查放在 `ci.yml`**：改標題時要整套 CI 重跑才會重新檢查。
