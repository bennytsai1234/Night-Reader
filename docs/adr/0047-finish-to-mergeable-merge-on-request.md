# 分支做到「可以合併」就停：收尾由使用者點頭，合併由使用者說

功能與維護在從 `beta` 開的分支上做。做的途中每段驗證過就 commit 並推上：推上是為了備份，這時不跑 CI（ADR 0048）。交代的事全部做完、驗證過，手上沒有待辦、也沒有要問使用者的事，才回報做了什麼，問使用者要不要收尾，選項是「Codex 審查後收尾」「不審直接收尾」「繼續改」。還有待辦就繼續做，有要使用者決定的事就先問那件事。這和 ADR 0014 原本「告一段落」的定義相同；2026-10-19 到 10-28 曾把「做完一步」也當成告一段落，一天開了四個 PR。

收尾依序做這些事：

1. Codex 審整條分支一次，核對屬實才修。只審 App 的程式或資源改了、而且不只是註解的分支；只改文件、網站、CI 與發版設定、hook、工具腳本、測試、註解的不審，問要不要收尾時也不提審查。使用者選了「不審」也不審。
2. 併入最新 `beta`。
3. 推上並等 CI 通過。
4. 開以 `beta` 為目標的 PR。
5. 刪掉 worktree 與本機分支。

做完回報「可以合併」，不合併。一條分支開一個 PR。

使用者說「合併」時，由一個 Agent 把可以合併的 PR 依序處理，這個角色叫合併 Agent：

- 併入最新 `beta`、解衝突。
- 有併進新東西就等 CI 通過；`beta` 從分支最後一次 CI 之後沒動過，就直接合併。
- squash 合併，刪掉遠端分支，換下一個。

合併 Agent 不審查，除了解衝突也不改程式。同一時間只有它寫 `beta`。

交接只在做到一半要換對話時寫（`handoff` 技能），收尾時刪掉，不帶進 `beta`；要交代的寫在 PR 說明與回報裡。

為什麼這樣定：2026-11-07 使用者定的。原本照 ADR 0014 做完就自己合併。使用者常同時開好幾個對話各做一條分支，先合併的會讓後面的要重新併入、重跑 CI，還會在 `CHANGELOG.md` 與 `HANDOFF.md` 上互相衝突。另外，Codex 審查、等 CI、開 PR 這一串很重，做到一半就跑，之後再改又要重來一次，所以等使用者確認做完才收尾。

2026-10-28 曾試過「說合併才合併」，隔天改回做完就合併，原因是量測工具的修正一直留在沒合併的分支上，`beta` 一直用舊工具。這次加了兩道防線：

- 接手的 Agent 開工時列出可以合併但還沒合併的 PR，提醒使用者一次。
- 別的分支要用到的修正（例如工具），收尾回報時說明「這條要先合」。

## 考慮過的做法

- **做完就合併**：ADR 0014 從 2026-10-29 起的做法。只有一個對話在做時順，同時開好幾個就互撞。
- **開發 Agent 做完自動派子代理合併**：兩個子代理同時合併還是會撞。
- **照發不發測試版的判斷（`app-files`）決定審不審**：ADR 0014 原本的做法。建置 APK 的 workflow 與只改註解都算進去，2026-11-07 一條只改發版設定、文件與一行註解的分支也被列成要審，使用者指出「只是一些文檔的更改，為什麼需要審查」。
- **合併時才派 Codex 審查**：合併 Agent 不知道那段程式的來龍去脈，核對與修正都得從頭讀。
- **多條分支併成一個 PR**：`beta` 上一筆紀錄混了好幾件事，出問題時只能一起撤。
- **合併時一律等 CI**：`beta` 沒動過時，分支的 CI 結果就是合併後的結果，再等一次是白等。
- **合併時一律不等 CI**：併進新東西後的組合沒人測過。發版前雖然會再跑 CI、壞了不發，但壞掉的 `beta` 要等到下一個人開工才會發現。
- **只在同時開好幾條分支時才停在可以合併**：Agent 判斷不了使用者有沒有另外開對話，規則要一致才不會漏。
