# 開發與發布流程

**分支**：`beta` 是預設分支，日常改動都進這裡。`main` 只快轉到使用者用過沒問題的 `beta` 提交，用來發正式版，自己不收提交。只改說明文件時直接在 `beta` 上改；程式改動在分支上做，同一段工作的改動放同一條分支、一個 PR，squash 合併（使用者 2026-11-14：原本一件事一條分支，同一批分析帶出的改動被拆成好幾條，不好管）。原型分支只用來讓使用者挑，不合併，選定後刪掉。使用者要「自己用過才上正式版」，`main` 只快轉，兩條就不必互相同步。

**收尾與合併**：開發的 Agent 等交代的事全部做完、沒有待辦才收尾，`feat/` 還要等使用者說這條沒問題。收尾是審查、併入最新 `beta`、開 PR、等 CI；CI 通過後由同一個 Agent 自己合併。審查、等 CI、開 PR 很重，所以等做完才跑。

合併前先看這條分支開出之後，`beta` 多了哪些 App 改動。沒有就直接 squash 合併。有的話，在本機把 `beta` 併進來跑 analyze 與受影響的測試；其中改到同一個模組的，再派 Codex 照四象限審相容性：這條分支的程式在它們的新行為下對不對，它們有沒有依賴這條分支改掉的東西。有修改才推上去重跑 CI，沒有就直接合；合之前 `beta` 又動過就再看一次，同時合併的對話因此會一個看到另一個。

為什麼要看：兩條分支各自的 CI 都過，合在一起沒人測過。2026-11-15 #389（書源校驗）與 #390（背景工作暫停）在 11 秒內先後合進 `beta`，一邊改了參數、另一邊照舊的呼叫，`beta` 編譯失敗，合併前的 analyze 就擋得住；編譯會過、行為上沒考慮到彼此的，靠相容性審查與使用者試測試版。2026-11-03～11-17 改到 App 的 125 個 PR 裡，74 個（59%）開到合之間有別的 App PR 先合進 `beta`，33 個（26%）改到同一個模組，22 個（18%）改到同一個檔案。

**審查**：只審動到資料與背景的分支（資料怎麼存、背景工作、書源引擎與規則解析、送出 App 的資料），派 Codex 審；範圍與做法在 `docs/agents/finish.md`。介面（版面、文字、圖示、動畫、骨架、主題）、文件、設定、CI、工具、測試與小修不審：審出的真 bug 集中在同步、背景工作、有聲書、漫畫這類，介面 PR 多半是註解與像素，文件與工具不進讀者手上的 App。

**CI**：只在開 PR、PR 有新推送、推上 `beta` 時跑，只改 `.md` 與 `docs/` 的不跑；做的途中推分支只是備份，不跑。全套測試只在 CI 跑，本機只跑受影響的測試、推送前跑 analyze。做到一半的 CI 結果沒有意義，而本機在 Windows 上跑全套要 5 到 10 分鐘。

**測試版**：使用者說「發測試版」時，確認 `beta` 最後一次 CI 通過（失敗就先修）再手動觸發，回報時列出這一批裡改到同一個模組的 PR 組合，讓使用者試的時候特別看。各自沒問題、合在一起才出錯的，`beta` 的 CI 擋在發布之前，讀者拿不到壞的版本。說明是這批改到 App 的 PR 標題，去掉前綴一個一行，所以 PR 標題要寫成讀者看得懂的一句，開 PR 時會檢查。App 行為沒變的提交標 `Release-Notes: none`，就不算 App 改動。每合一次就發一版時，手機一天跳了 15 次更新；每個 PR 都要寫一條更新說明時，一週約有 20 次因為沒寫或太長而失敗。

**正式版**：使用者說要發才發。在 `beta` 推一個升版號的提交，同時在 `CHANGELOG.md` 加上 `## X.Y.Z`：從上一個正式版之後的 PR 標題整理成一兩句介紹加最多八條，不寫書源名稱與網址。再把 `main` 快轉過去。

**版號**：tag 只由 CI 建立（ADR 0002）。正式版是 `vX.Y.Z`；測試版是 `vX.Y.(Z+1)-beta.N`，`N` 是正式版之後的提交數。versionCode 取發版那個提交的提交數，`beta` 與 `main` 是同一條歷史，所以只增不減，裝了測試版也升得到正式版。分支保護只禁止強制推送與刪除，就是為了不改寫歷史。只建測試 APK 時取 `beta` 上最近一個發出去的版本的提交數：分支的提交合併時會 squash，分支自己的提交數可能比之後的測試版還大；`beta` 最新的提交也常比最近的發布多幾個只改文件的提交。取最近發布的數字，測試 APK 和目前的版本一樣大，裝完還裝得回去。

## 考慮過的做法

- **做到「可以合併」就停，使用者說「合併」才由一個合併 Agent 依序合**（2026-11-07～11-18）：原本是怕同時開好幾個對話各自合併會互撞（重併、重跑 CI、CHANGELOG 與 HANDOFF 衝突）。後來 CHANGELOG 只在發正式版時改，交接寫在分支上、合併前刪掉，`beta` 動過也不重跑 CI，互撞只剩真的衝突與合在一起才壞的組合；依序合擋不住後者（上面 11-15 那次就是合併 Agent 連著合的），分支還要等使用者開口才合。使用者 2026-11-18 改成各自審完自己合併，加上合併前的相容性檢查。
- **說「合併」才合併，卻沒有提醒**：2026-10-28 試過，工具的修正一直留在分支上沒合，`beta` 一直用舊的。
- **`beta` 動過就一律把它併進 PR、重跑 CI 再合**：每個 PR 合之前都測過併進最新 `beta` 的樣子，但一批 N 個要多等 N−1 輪，2026-11-02 一天合了 47 個。現在只在 `beta` 多了 App 改動時才在本機併進來檢查，有修改才重跑 CI。
- **GitHub 自動合併**（`gh pr merge --auto`）：CI 一過就合，中間沒機會做相容性檢查。合併佇列只開放給組織擁有的 repo，夜讀在個人帳號下用不了。
- **多條分支併成一個 PR**：一筆紀錄混了好幾件事，出問題只能一起撤。
- **另一個 applicationId 的「夜讀 Beta」**：可以和正式版並存，但書源與書架要另外匯入一次。
