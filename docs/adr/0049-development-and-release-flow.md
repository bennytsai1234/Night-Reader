# 開發與發布流程

**分支**：`beta` 是預設分支，日常改動都進這裡。`main` 只快轉到使用者用過沒問題的 `beta` 提交，用來發正式版，自己不收提交。只改說明文件時直接在 `beta` 上改；程式改動一件事一條分支、一個 PR，squash 合併。原型分支只用來讓使用者挑，不合併，選定後刪掉。使用者要「自己用過才上正式版」，`main` 只快轉，兩條就不必互相同步。

**收尾與合併**：開發的 Agent 等交代的事全部做完、沒有待辦，才問要不要收尾。收尾是審查、併入最新 `beta`、開 PR、等 CI，做到「可以合併」就停。使用者說「合併」時，由一個合併 Agent 依序合併；`beta` 沒動過就不重等 CI。合完一批後等 `beta` 的 CI 通過，失敗就留下來修。使用者常同時開好幾個對話，各自合併會互撞，所以由一個 Agent 依序合；審查、等 CI、開 PR 很重，所以等做完才跑。

**審查**：只審 App 的程式或資源有改、而且不只是註解的分支，派 Codex 審，審不審由使用者選。文件、設定、CI、工具、測試不進讀者手上的 App，審了沒有收穫。

**CI**：只在開 PR、PR 有新推送、推上 `beta` 時跑；做的途中推分支只是備份，不跑。全套測試只在 CI 跑，本機只跑受影響的測試、推送前跑 analyze。做到一半的 CI 結果沒有意義，而本機在 Windows 上跑全套要 5 到 10 分鐘。

**測試版**：合併 Agent 合完一批、`beta` 的 CI 通過後手動觸發，一批發一版。說明是這批改到 App 的 PR 標題，去掉前綴一個一行，所以 PR 標題要寫成讀者看得懂的一句，開 PR 時會檢查。App 行為沒變的提交標 `Release-Notes: none`，就不算 App 改動。每合一次就發一版時，手機一天跳了 15 次更新；每個 PR 都要寫一條更新說明時，一週約有 20 次因為沒寫或太長而失敗。

**正式版**：使用者說要發才發。在 `beta` 推一個升版號的提交，同時在 `CHANGELOG.md` 加上 `## X.Y.Z`：從上一個正式版之後的 PR 標題整理成一兩句介紹加最多八條，不寫書源名稱與網址。再把 `main` 快轉過去。

**版號**：tag 只由 CI 建立（ADR 0002）。正式版是 `vX.Y.Z`；測試版是 `vX.Y.(Z+1)-beta.N`，`N` 是正式版之後的提交數。versionCode 取發版那個提交的提交數，`beta` 與 `main` 是同一條歷史，所以只增不減，裝了測試版也升得到正式版。分支保護只禁止強制推送與刪除，就是為了不改寫歷史。只建測試 APK 時取 `beta` 的提交數：分支的提交合併時會 squash，分支自己的提交數可能比之後的測試版還大，裝了就裝不回去。

## 考慮過的做法

- **做完就自己合併**：只有一個對話在做時順，同時開好幾個就互撞。
- **說「合併」才合併，卻沒有提醒**：2026-10-28 試過，工具的修正一直留在分支上沒合，`beta` 一直用舊的。所以現在使用者說「繼續」時，會列出可以合併的分支。
- **多條分支併成一個 PR**：一筆紀錄混了好幾件事，出問題只能一起撤。
- **另一個 applicationId 的「夜讀 Beta」**：可以和正式版並存，但書源與書架要另外匯入一次。
