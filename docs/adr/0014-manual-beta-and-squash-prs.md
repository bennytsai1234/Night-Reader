# 測試版手動發布；App 改動走 PR，合併前 Codex 審查並把摘要貼在 PR 上，squash 合併

測試版不再隨推上 `main` 自動發布：`main` 收到改動只跑 CI，維護者說要發時，以 `channel=beta` 手動執行 `android-release.yml`，把上一個發布之後累積的改動發成一個測試版（tag 與 versionCode 的算法照 ADR 0004）。正式版不變，仍由升版號的 commit 推上 `main` 觸發（ADR 0002）。更新說明也改在手動發測試版的那一刻檢查：上一個發布的 tag 之後改到 App 內容，`CHANGELOG.md` 的「未發布」就要跟著寫（ADR 0010 的檢查規則不變，只是時機從每次推送改成發版）。

所有改動都在分支上做，交接文件、文件錯字這類小改動也一樣；不急的小改動就在分支上累積，等下一次較大的更新一起進 `main`。維護者說合併時：

1. 這次要合併的分支（可以是好幾條）併成一條，推上去，開一個 PR。
2. Codex 審整個 PR 一次，核對屬實的問題修在同一個 PR，再把審查摘要貼成 PR 留言：發現了什麼、核對結果、修了哪些、沒修的為什麼。
3. 合併前先把最新的 `main` 併進分支：開 PR 之後 `main` 有新的提交（例如另一個 PR 先合併了），就併進來、解完衝突推上去，等 CI 在合併後的狀態重新跑過。
4. CI 通過後用 squash 合併；squash commit 的說明寫整個 PR 做了什麼、為什麼。分支在合併後由 GitHub 自動刪除。

`main` 上一次合併只留一個 commit，逐步的 commit 與說明永久留在 PR 頁面。GitHub 上 `main` 不強制只能經 PR 合併，只禁止強制推送與刪除（ADR 0004）；走 PR 是約定。

為什麼這樣定：2026-10-09 曾改成走 PR（#19），2026-10-11 又改回直接推 `main`（`e9a37a6`），理由是只有一個人開發、PR 沒人審，只多一趟來回；之後又因為每次推 `main` 都發測試版，改成在分支上累積（`52fca36`）。這兩個問題現在分開解決：發不發版改由手動決定，推 `main` 就不再等於發版；PR 則有了實際用途，Codex 的審查摘要與修正記在 PR 上，squash 讓 `main` 的紀錄一個 PR 一行，細節不會因為合併後刪分支而遺失。審查摘要貼在 PR 上是使用者在幾種做法裡選的（只在對話裡回報、貼在 PR 上、不固定審查）；小改動在分支上累積、多條分支合成一個 PR，也是使用者定的，讓 `main` 的紀錄與每次合併的審查都以一批更新為單位。合併前併入最新 `main` 是 2026-10-14 補的：CI 只在推送分支時跑，驗證的是分支本身；兩個 PR 同時開著、改的地方不重疊時，GitHub 會讓後一個直接合併，但它的 CI 是在前一個合併之前的 `main` 上跑的，兩邊各自通過、合在一起才壞的情況要到推上 `main` 才會發現。以上反覆的來回讓使用者很困擾，之後要改這套流程，先改這份 ADR。

## 考慮過的做法

- **維持推上 `main` 就自動發測試版，小改動在 commit 標記跳過**：忘了標記就多發一版，使用者會收到內容沒差多少的更新通知。
- **每天定時發測試版**：不用記得觸發，但改完要等到固定時間才拿得到。
- **在本機合併、保留每個 commit、不開 PR**：`main` 的紀錄很長；squash 要保留細節就得留著 PR 頁面，不開 PR 時合併後刪掉分支，細節就沒了。
- **GitHub 強制只能經 PR 合併、CI 必須通過**：只有一個人開發，約定就夠。
- **一條分支一個 PR**：一批相關的更新要開好幾個 PR、各審一次，`main` 上也多好幾個 commit。
