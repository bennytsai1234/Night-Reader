# 測試版手動發布；功能與維護走 PR、文件直接改 main，合併前 Codex 審查並把摘要貼在 PR 上，squash 合併

> 分支與發測試版的時機已由 ADR 0027 取代：PR 與只改文件的提交都進 `beta`，推上 `beta` 就自動發測試版，`main` 只快轉到 `beta` 上的提交發正式版。PR 的審查、squash 合併、交接與原型分支照本文，本文的 `main` 讀作 `beta`。

測試版不再隨推上 `main` 自動發布：`main` 收到改動只跑 CI，維護者說要發時，以 `channel=beta` 手動執行 `android-release.yml`，把上一個發布之後累積的改動發成一個測試版（tag 與 versionCode 的算法照 ADR 0004）。正式版不變，仍由升版號的 commit 推上 `main` 觸發（ADR 0002）。更新說明也改在手動發測試版的那一刻檢查：上一個發布的 tag 之後改到 App 內容，`CHANGELOG.md` 的「未發布」就要跟著寫（ADR 0010 的檢查規則不變，只是時機從每次推送改成發版）。

只改說明文件（`README.md`、`DESIGN.md`、`GLOSSARY.md`、`CODING_STANDARDS.md`、`AGENTS.md`、`HANDOFF.md`、`docs/`）時直接在 `main` 上改，不開分支、不審。新功能與維護（程式、測試、CI、hook、`pubspec.yaml`、`website/`）在分支上做、走 PR；跟著功能一起改的文件放在同一個 PR。`HANDOFF.md` 只寫從 repo 與 GitHub 查不到、而且還沒收尾的事（還沒合併的工作、等維護者決定的事、還沒寫進其他文件的決定），不寫合併了什麼、發了哪一版；環境上的坑是長期有效的事實，寫在 `AGENTS.md`「環境」（2026-10-21 起，原本放在交接裡）。交代的目標做完、驗證過，也沒有等維護者決定的事，就是告一段落，直接合併，不問維護者要不要合併：

1. 這次要合併的分支（可以是好幾條）併成一條，推上去，開一個 PR。
2. Codex 審整個 PR 一次，核對屬實的問題修在同一個 PR，再把審查摘要貼成 PR 留言：發現了什麼、核對結果、修了哪些、沒修的為什麼。
3. 在同一個 PR 裡把 `HANDOFF.md` 改成合併後的狀態；合併之後不再另外補交接。
4. 合併前先把最新的 `main` 併進分支：開 PR 之後 `main` 有新的提交（例如另一個 PR 先合併了），就併進來、解完衝突推上去，等 CI 在合併後的狀態重新跑過。
5. CI 通過後用 squash 合併；squash commit 的說明寫整個 PR 做了什麼、為什麼。PR 的分支在合併後由 GitHub 自動刪除，併進這個 PR 的其他分支（本機與遠端）合併後一起刪掉。

原型（`prototype` 技能做的拋棄式網頁或程式）放在自己的分支，不合併；維護者選定、結果寫進 `DESIGN.md` 或 ADR 之後就刪掉分支，不另外保存。

`main` 上一次合併只留一個 commit，逐步的 commit 與說明永久留在 PR 頁面。GitHub 上 `main` 不強制只能經 PR 合併，只禁止強制推送與刪除（ADR 0004）；走 PR 是約定。

為什麼這樣定：2026-10-09 曾改成走 PR（#19），2026-10-11 又改回直接推 `main`（`e9a37a6`），理由是只有一個人開發、PR 沒人審，只多一趟來回；之後又因為每次推 `main` 都發測試版，改成在分支上累積（`52fca36`）。這兩個問題現在分開解決：發不發版改由手動決定，推 `main` 就不再等於發版；PR 則有了實際用途，Codex 的審查摘要與修正記在 PR 上，squash 讓 `main` 的紀錄一個 PR 一行，細節不會因為合併後刪分支而遺失。審查摘要貼在 PR 上是使用者在幾種做法裡選的（只在對話裡回報、貼在 PR 上、不固定審查）；多條分支合成一個 PR 也是使用者定的，讓 `main` 的紀錄與每次合併的審查都以一批更新為單位。合併前併入最新 `main` 是 2026-10-14 補的：CI 只在推送分支時跑，驗證的是分支本身；兩個 PR 同時開著、改的地方不重疊時，GitHub 會讓後一個直接合併，但它的 CI 是在前一個合併之前的 `main` 上跑的，兩邊各自通過、合在一起才壞的情況要到推上 `main` 才會發現。交接跟著 PR 一起合併、只寫查不到的事、合併後清掉併入的分支與用完的原型，是 2026-10-14 合併 #61 之後使用者同意的：原本合併後才補交接，又照規則放在新分支等下一次合併，`main` 上的交接永遠落後一次合併（#61 合併後還寫著「進行中」）；交接裡的「最近合併」與發版編號在 PR 頁面與 GitHub Actions 都查得到，只是重複；GitHub 只自動刪 PR 本身的分支，併進來的分支與原型分支一直留在遠端。只改文件時直接改 `main` 是 2026-10-15 使用者定的：原本文件也要在分支上累積、等下一次合併，是因為當時推 `main` 就發測試版；測試版改成手動發之後這個理由已經不在，發版檢查也不把文件算成 App 改動，文件交給 Codex 審沒有實際收穫，留在分支上只會讓 `main` 上的規範與交接落後。告一段落就直接合併是 2026-10-19 使用者定的：原本要等維護者說合併，每次做完都要問一次，使用者不想再被問；還有要問維護者的事就還沒告一段落，所以不必另外判斷時機。以上反覆的來回讓使用者很困擾，之後要改這套流程，先改這份 ADR。

## 考慮過的做法

- **維持推上 `main` 就自動發測試版，小改動在 commit 標記跳過**：忘了標記就多發一版，使用者會收到內容沒差多少的更新通知。
- **每天定時發測試版**：不用記得觸發，但改完要等到固定時間才拿得到。
- **在本機合併、保留每個 commit、不開 PR**：`main` 的紀錄很長；squash 要保留細節就得留著 PR 頁面，不開 PR 時合併後刪掉分支，細節就沒了。
- **GitHub 強制只能經 PR 合併、CI 必須通過**：只有一個人開發，約定就夠。
- **合併後另開分支補交接**：`main` 上的交接要等到下一次合併才更新，中間開工的人讀到的是舊狀態。
- **原型移進 repo 保存（例如 `docs/prototypes/`）**：選定之後沒有人會再更新它，決定本身已經寫在 `DESIGN.md` 或 ADR。
- **文件也在分支上累積，跟下一次較大的更新一起合併**：2026-10-15 以前的做法；推 `main` 不再發版後，只剩讓文件晚生效、多一趟 PR。
- **一條分支一個 PR**：一批相關的更新要開好幾個 PR、各審一次，`main` 上也多好幾個 commit。
