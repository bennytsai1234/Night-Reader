# 收尾

照 `plan` 技能第 5 步「收尾合併」，夜讀另外照這些；要不要審照這裡的範圍。為什麼見 ADR 0049。

- **要不要審**：只審動到資料與背景的分支：資料怎麼存（資料庫、備份、同步）、背景工作、書源引擎與規則解析、送出 App 的資料（AI、日誌、分享）。常見的目錄列在 `AGENTS.md`「開發設定」的高風險，沒列到的照這幾類判斷。介面（版面、文字、圖示、動畫、骨架、主題）、文件、網站、CI、工具、測試與小修不審，也不問。使用者 2026-11-21 定的：11-01～11-21 的 222 條 PR，Codex 審出的真 bug 集中在同步、背景工作、有聲書、漫畫這類，介面 PR 多半是註解與像素；約 850 項修掉的只有 5 項指出共同的根本原因。這和發不發測試版是兩回事，不看 `tool/changelog.sh app-files`。
- **先理狀態**：要審的這類分支，好幾個狀態互相牽動時，開工前先照 `docs/state-machines.md` 理成狀態機。審查是最後補漏，不是事後一個一個補洞（背景搜尋那次一審 17 項，幾乎都是旗標互相牽動）。
- **審查**：`review` 技能，沒有 Codex 的環境改派另一個子代理審。觸點清單用 `docs/agents/new-feature.md` 的「觸點」表，該進備份、同步的沒接上算會碰到的 bug。核對屬實的修掉，修完只重跑這次修正改到的測試檔。
- **PR**：目標 `beta`；說明照 `pr` 技能用繁體中文寫，有審查就寫一段「審查」（發現了什麼、核對結果、修了哪些、沒修的為什麼）。
- **PR 標題**：改到 App 內容的 PR，標題去掉 `fix(reader): ` 這類前綴就是測試版說明的一行。寫一般讀者看得懂的一句，不寫內部實作、具名書源與網址，145 字以內，`pr-title.yml` 會檢查。App 行為沒變的（例如只改註解、只改發版設定）在 PR 說明裡單獨一行寫 `Release-Notes: none`，就不進測試版說明。
- **等 CI**：開 PR 後用 T3 的 PR 監看（`watch_pull_request`），結束這一輪；喚起時有一項失敗就看原因、修好重推，全部通過就照 `docs/agents/merge.md` 合併。
- **改到 `android/`、`ios/` 的原生程式**：PR 的 CI 不建置 APK，Kotlin 編不編得過要另外跑 `gh workflow run android-release.yml --ref <分支> -f channel=test`（只建 APK 與 IPA、不發布），通過才合併。
