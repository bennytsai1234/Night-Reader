# 動畫儀表板

使用者看儀表板判斷動畫的問題在哪；動畫實際好不好看，使用者在手機上看。頁面的版型就是 `tool/frame_viewer/template.html`：上面幾支手機同步逐格播放（含「目前」當對照），下面是分段色條、每格的畫面變化、指定位置的深淺、每格主執行緒花的時間（其中測試的資料庫另外標出）與其中回收記憶體停住多久，點圖跳到那一格，點手機換成那一支的資料。

## 步驟

1. **錄影**：在 `test/_screens/`（git 忽略）寫一個臨時測試，用 `test/support/frame_recording.dart` 的 `recordAnimation` 錄；寫法、檔名規則與量測的限制在那個檔的檔頭。每個候選（含目前）× 每個變化 × 淺色、深色各錄一段；整個 App 的動畫先開一次暖身再錄。每個候選只錄一次，錄到問題就修，不為了確認穩不穩定連錄好幾次。`phase()` 回傳的段落名稱要和下一步設定檔 `phases` 的鍵一模一樣。測試放背景跑（`FRAME_GC=1 flutter test --enable-vmservice test/_screens/<檔名>_test.dart`，一般一兩分鐘；`FRAME_GC` 讓頁面多一排每格的回收記憶體）。
   完成：`%TEMP%\night-reader-frames\` 下每一段都有 `frames.rgba` 與 `meta.json`，從 `meta.json` 的 `phases` 列出每段的起訖格核對過：開頭有動畫開始前的那段，結尾錄到動畫播完後的靜止畫面（`until` 成立時動畫可能還在播，`tailFrames` 要蓋過剩下的時長），每段的格數和程式裡的時長對得上（一格 8.3ms）。

2. **設定檔**：寫在 repo 外（例如 `%TEMP%\night-reader-frames\<主題>.json`），照 `tool/frame_viewer/example.json`（開 App 進場的實例）改；每個欄位的意思在 `tool/frame_viewer/build.py` 的檔頭。每一段都寫說明（`notes`），用使用者的詞講這段畫面在做什麼、主執行緒在忙什麼；這是頁面上讓使用者讀懂時間軸的地方。
   完成：每個錄到的段落名稱都有對應的 `phases` 鍵與說明。

3. **做頁面**：`python tool/frame_viewer/build.py <設定檔>`，輸出 `viewer/page.html`。把 `page.html` 的內容整份交給 `html_preview`：主控台沒有錯誤、拼圖逐格對得上、色條分段和說明對得上；再用它回報的高度交給 `html_render`。
   完成：儀表板已經放在對話裡。

   判讀照 ADR 0036 的三條標準：點下去的那一格可以重；預留停頓（畫面靜止）可以跑重的工作；動畫在動的每一格連同回收記憶體都要在上限內（手機 8.3ms，電腦照 2 倍換算是 4.2ms，`limitMs`）。判讀尖峰前先確認它是 App 的成本：
   - 「畫面變化」在畫面該靜止的段落冒出尖刺，先看每個像素差多少、落在哪裡。定格換場播完換回真畫面那一格應該是 0（ADR 0035）；不是 0 時，是拍好之後底下又變了，或拍法改回了 `toImageSync`。
   - 主執行緒那排的柱子上面淺色那段不算進判斷：測試的資料庫（`db_clock.dart`，手機上不在主執行緒），以及閱讀器排版切片的一半（`slice_clock.dart`；排版照時間切，每格做到預算就停，手機上一樣長，照實算、不乘 2）。柱子只在畫面在變的幀（ADR 0037，照圖層判斷）用扣掉後的值和上限比，標成掉幀的顏色；畫面沒在變時超過的是灰色、不算。資料庫時間只會少算，所以扣掉後還超過的一定是 App 自己的工作。錄影每幀存畫面，量到的時間比 `test/frame_budget/` 多 0.3–0.5ms，貼著上限的幀照 `test/frame_budget/` 的數字判斷。
   - 「回收記憶體」那排的柱子落在動畫在動的段落：回收本身可以有，看那一格連同回收有沒有超過上限。測試裡沒有手機趁兩格空檔做的回收，回收落在哪一格會和手機不同，看的是有多少要回收、有沒有先在畫面靜止時清掉。
   - 超過上限的格子落在畫面靜止的段落（例如骨架長完、換場前停住的那幾格）不是問題，也不要把「靜止停得比較久」列成瑕疵：那是預留停頓，重的工作放在靜止的畫面上，換來動畫在動的每一格都輕。
   - 動畫中超過上限的格子，加 `FRAME_PHASES=1`（或 `FRAME_ATTRIBUTE=1`）用 `test/frame_budget/` 的同一情境跑一次，看時間落在哪一步、誰在重建，查出原因就修；不連跑好幾次確認是不是每次都有。

4. **回覆**：頁面已經畫出的不再重述，只補頁面說不出的：尖峰在哪一段、為什麼、你的判斷與建議。改前改後的比較加一張表：每段掉幀的幀數（ADR 0037：畫面在變時，扣掉資料庫、排版切片照實算後超過 4.2ms）、開始到畫面穩定的時間；不列最忙的一幀，降了但還超過一樣是掉幀。

5. **收尾**：刪掉自己這次在 `%TEMP%\night-reader-frames\` 的錄影與 `viewer/`，以及 `test/_screens/` 裡這次的臨時測試。
